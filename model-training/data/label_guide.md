# 라벨 규칙 (학습 데이터 정답 기준)

Gemma 4 E4B 파인튜닝용 정답 데이터를 만들 때 따르는 규칙입니다.
**정답이 흔들리면 모델도 흔들립니다.** 애매한 문장은 이 문서에 규칙을 추가한 뒤 라벨링하세요.

| 과제 | 대상 | 데이터 파일 |
|---|---|---|
| 1. 챗봇 툴 선택 + 인자 추출 | `dcm-back/app/agent.py` 의 **모드 0 (접수·조회)** | `chat_records.jsonl` |
| 2·3. 민원 분석 (카테고리·요약·핵심어) | `dcm-back/app/ai.py` 의 `analyze()` | `analysis_records.jsonl` |

**학습하지 않는 것**
- 챗봇 **모드 1 (문의)**: 업무 지식 답변을 학습하면 낡거나 지어낸 정보가 나오고, 거절·안내 예시만 넣으면
  진짜 문의까지 거절하는 쪽으로 치우칩니다. 나중에 FAQ 검색(RAG)을 붙일 때 다시 다룹니다.
  (모드 0 학습 후 모드 1 답변이 망가지지 않았는지는 평가에서 몇 문장으로 확인합니다)
- CSV 헤더 매핑(`infer_csv_mapping`)

---

## 공통 규칙

- **원문에 없는 내용을 만들지 않습니다.** 날짜·기관·장소·법령·해결책을 추측해 넣지 않습니다.
- 개인정보(전화번호·이메일·주민등록번호)는 앱이 LLM 에 넘기기 전에 `[개인정보 제외]` 로 가립니다.
  정답 데이터의 원문도 같은 형태여야 합니다.
- 카테고리는 `dcm-back/app/categories.py` 의 7종 정의(괄호 안 경계 규칙 포함)를 따릅니다.
  backend `training/records.py` 머리말의 카테고리 경계 규칙과 같은 기준입니다.
- 같은 원문을 말만 바꿔 늘린 변형은 같은 `group` 으로 묶습니다.
  같은 group 은 반드시 같은 쪽(학습/검증/평가)에 들어가 평가 점수가 부풀지 않습니다.

## 과제 1. 챗봇 모드 0 (접수·조회)

### 1-1. 툴 선택

| # | 사용자 발화 | 정답 | 출처 |
|---|---|---|---|
| A1 | 행정기관이 알고 조치하거나 참고하기를 바라는 일을 전함 - 불편·문제·피해·위험, 처리 지연·절차 불편, 개선 요구·제안, 공무원·공공서비스 칭찬·감사 (접수) | `insertRequestT` | backend `records.jsonl` 의 `접수` |
| A2 | 이미 낸 자기 민원을 다룸 - 처리 상황 확인, 내용 변경·보충, 취소·철회 | `selectComplaintT` | backend `조회`·`수정`·`삭제` |
| A3 | 접수 의사만 있고 내용이 없음 ("민원 넣고 싶어요") | `insertRequestT(title="", content="")` | 새로 작성 (`c-a3-*` 150건 + `c-bal-a3-*` 450건) |
| A4 | 잡담·광고·무의미한 말 | 툴 없이 거절 문구 (A15) | backend `해당없음` + `c-bal-oos-*` 155건 |
| A5 | 문의 ("민원실 몇 층이에요?") | 툴 없이 문의 모드 안내 문구 (A16) | backend `문의` + `c-bal-inq-*` 264건 |

**A1~A5 는 챗봇 시스템 프롬프트(`prompts.py` 의 [도구 선택])와 같은 기준입니다.** 프롬프트는 단어가 아니라 **의도**로 고르게 쓰여 있고,
의도가 여러 개로 보이면 A2 → A1 → A3 → A5 → A4 순서로 먼저 맞는 것을 고릅니다. 라벨 기준을 바꾸면 프롬프트도 같이 고치세요 (프롬프트 v7 부터).

- 행정 업무의 처리 지연·절차 불편을 알리는 말(전입신고가 안 돼요 등)은 **접수**입니다.
- 장소·세부 내용이 부족하거나 말투가 감정적이거나 질문으로 끝나도, 전하려는 구체적인 사정이 있으면 **접수**입니다. (장소가 없는 것은 분석의 `needs_review` 가 잡습니다)
- 칭찬·감사·제안도 전하려는 내용이 있으면 **접수**, 내용 없는 인사·감사 표현만 있으면 **거절**입니다.
- 이미 낸 자기 민원에 대한 말이면 새로 생긴 사정을 덧붙여도 **조회**입니다. 자기 민원을 가리키지 않는 일반 질문(민원 취소가 가능한지 등)은 **문의**입니다.
- 이 창구에 이미 넣은 민원의 진행을 묻는 말("제가 넣은 OO 민원 처리됐나요")은 **조회**입니다.
- **A3 와 문의의 경계**: 접수하겠다는 의사 표시("민원 넣을게요", "신고하려고요", "접수 양식 열어 주세요")만 있으면 **A3**,
  접수 방법·조건을 묻는 말("민원은 어떻게 접수해요?", "주말에도 접수되나요?")은 **문의**입니다.
  A3 에는 물음표로 끝나는 방법 질문을 넣지 않습니다. 대상만 살짝 언급한 말("집 앞 일로 민원 넣고 싶어요")도
  무엇이 문제인지 없으면 A3 입니다.

### 1-2. 툴 인자

| # | 인자 | 규칙 | 예 |
|---|---|---|---|
| A6 | `insertRequestT.title` | 무엇이 어떤 상태인지 짧은 명사형. 위치·기간·요청 문구("~요청", "~조치")는 넣지 않음. **대상(무엇)은 발화에 나온 말**을 쓰고, 상태는 짧은 명사(파손·고장·지연·미지급 등)로 줄여도 됨. 발화에 없는 대상·종류("벌레"→"러브버그", "수급비"→"생계급여")나 진단·법적 판단(저장강박·방임·학대·일조권 침해·산재 등)은 넣지 않음. 층간소음·무단투기처럼 말한 상황을 그대로 가리키는 일상어는 써도 됨 | "공원 벤치 파손" |
| A7 | `insertRequestT.content` | **사용자 발화 원문 그대로** (인사말 포함, 가공하지 않음) | "한빛힐스에 사는 주민인데요, 학산어린이공원 벤치 나무가 썩어서 부서졌어요. 고쳐 주세요" |
| A8 | `selectComplaintT.content` | 찾을 민원의 **대상 명사만** 원문 그대로. backend 의 `arguments.keyword` 를 그대로 사용. 번호·동·호·층·장소 수식·상태·요청 말은 뺌. 대상을 알 수 없으면 `""` | "101동 엘리베이터 고장 민원 취소" → "엘리베이터", "어제 넣은 거 취소해 줘" → `""` |
| A9 | (없앰) `selectComplaintT.is_described` | `content` 가 비었는지로 똑같이 알 수 있어 인자를 없앴습니다 (프롬프트 v6). 앱은 `content` 가 `""` 이면 검색하지 않음 | |

- 수정 요청의 새 내용·새 위치(backend 의 `content`·`location`)와 `period`·`category`·`complaint_id` 는
  complaint-ai 툴에 해당 인자가 없으므로 **쓰지 않습니다.**
- 민원 ID·번호를 묻거나 언급하지 않습니다. (시스템 프롬프트 규칙)

### 1-3. 툴 호출 뒤 안내 문장 (두 번째 응답)

툴 결과에 따라 아래 **정해진 문구**를 정답으로 씁니다. 문구 원본은 `dcm-back/app/prompts.py` 의 `REPLY_TEXTS` 이고, 챗봇 시스템 프롬프트에도 같은 문구가 들어갑니다. 학습 샘플을 만들 때 툴 결과(민원 목록 등)는 가짜로 만들어 넣습니다.

| # | 상황 | `reply_kind` | 정답 문구 |
|---|---|---|---|
| A10 | 접수, 내용 있음 | `insert_filled` | 말씀하신 내용으로 접수 양식을 채워 두었어요. 왼쪽 양식을 확인하시고 '접수' 버튼을 눌러 주세요. 고칠 부분이 있으면 직접 수정한 뒤 접수하시면 됩니다. |
| A11 | 접수, 내용 없음 | `insert_empty` | 왼쪽에 접수 양식을 열어 두었어요. 불편하신 내용을 적고 '접수' 버튼을 눌러 주세요. |
| A12 | 조회, 결과 있음 | `select_found` | 말씀하신 내용과 비슷한 민원을 왼쪽에 보여 드렸어요. 접수 대기·진행 중인 민원은 수정하거나 삭제할 수 있고, 처리가 끝났거나 취소된 민원은 조회만 할 수 있어요. |
| A13 | 조회, 결과 없음 | `select_none` | 말씀하신 내용과 비슷한 민원을 찾지 못했어요. 민원 내용을 조금 더 자세히 알려 주시겠어요? |
| A14 | 조회, 대상 없음 (`content=""`) | `select_undescribed` | 어떤 민원인지 내용을 알려 주세요. (예: '집 앞 가로등 고장 민원') |
| A15 | 거절 (A4) | `reject` | 죄송하지만 민원 접수·조회와 관련된 내용만 도와드릴 수 있어요. |
| A16 | 문의 안내 (A5) | `inquiry_redirect` | 궁금하신 점은 '문의' 모드에서 물어봐 주세요. |

- `select_found` 와 `select_none` 은 같은 발화라도 툴 결과에 따라 달라지므로, 학습 샘플 생성기가
  `content` 가 있는 조회 레코드마다 결과 있음/없음 중 하나를 골라 만듭니다. 레코드에는 적지 않습니다.
- 문구를 바꾸면 다시 학습해야 합니다.

### 1-4. `chat_records.jsonl` 형식

한 줄에 발화 하나.

```json
{"id": "c-r01220", "group": "reg-203", "text": "한빛힐스에 사는 주민인데요, 학산어린이공원 벤치 나무가 썩어서 부서졌어요. 고쳐 주세요",
 "tool": "insertRequestT", "arguments": {"title": "공원 벤치 파손", "content": "한빛힐스에 사는 주민인데요, 학산어린이공원 벤치 나무가 썩어서 부서졌어요. 고쳐 주세요"},
 "source": "backend:r01220"}
{"id": "c-f01503", "group": "can-9-민원 건-r12", "text": "안녕하세요. 마지막으로 신고했던 민원 건 이제 처리 안 하셔도 돼요. 차주랑 연락이 됐어요",
 "tool": "selectComplaintT", "arguments": {"content": ""},
 "source": "backend:f01503"}
{"id": "c-r00006", "group": "oos-058", "text": "중고차 최저가 매입합니다",
 "tool": null, "arguments": null, "reply_kind": "reject", "source": "backend:r00006"}
```

| 필드 | 필수 | 내용 |
|---|---|---|
| `id` | ✅ | 고유 id. backend 에서 변환한 것은 `c-<backend id>` |
| `group` | | 변형 묶음. 없으면 id |
| `text` | ✅ | 사용자 발화 |
| `tool` | ✅ | `insertRequestT` / `selectComplaintT` / `null`(툴 없음) |
| `arguments` | 툴이 있을 때 ✅ | 위 1-2 규칙 |
| `reply_kind` | 툴이 없을 때 ✅ | `reject` / `inquiry_redirect` |
| `source` | | `backend:<id>` 또는 `new` |
| (균형 보강) | | `c-bal-*` 레코드는 `tags: ["균형보강"]`. 접수(내용 없음)·문의 안내·거절이 적어 새로 쓴 것 (아래 1-6) |
| `split` | | `train` / `val` / `test` 로 강제할 때만 |
| `tags` | | 자유 태그 (backend 에서 옮겨 옴. 예: `경계` = 헷갈리기 쉬운 문장) |

### 1-5. backend `records.jsonl` 변환 규칙

backend `records.jsonl`(5,058건)을 아래 규칙으로 변환해 둔 결과가 `chat_records.jsonl` 입니다. (`records.py` 검증 통과)
접수 2,025 / 조회 대상 있음 1,620 / 조회 대상 없음 640 / 거절 428 / 문의 안내 345

| backend `intent` | `tool` | `arguments` / `reply_kind` |
|---|---|---|
| 접수 | `insertRequestT` | `title` = `arguments.content`, `content` = `text` |
| 조회·수정·삭제 | `selectComplaintT` | `content` = `arguments.keyword` |
| 해당없음 | `null` | `reply_kind` = `reject` |
| 문의 | `null` | `reply_kind` = `inquiry_redirect` |

`id`·`group`·`split` 은 그대로 옮깁니다. backend 의 `category` 는 과제 1 에서 쓰지 않습니다.

### 1-6. 종류 균형 보강 (`c-bal-*`, 869건 - v8 에서 중복 정리, 아래 "v8 데이터 정리" 참고)

정답 종류 6가지의 건수 차이가 커서(접수 2,025 vs 접수(내용 없음) 150) 적은 종류를 새로 써서 600건 안팎으로 늘렸습니다.

| 종류 | 추가 | 만드는 법 | group |
|---|---|---|---|
| 접수(내용 없음) A3 | 450 | 접수 의사 표현 30가지 × 장소만 살짝 말하는 앞말("학교 앞 일로", "회사 일로" 등 - 무엇이 문제인지는 없음) × 인사말·말끝 변형. 물음표로 끝나는 방법 질문은 넣지 않음 | 같은 의사 표현끼리 `bal-a3-vNN` |
| 문의 안내 A5 | 264 | 제도·절차·위치·시간을 묻는 일반 문의 88문장 × 인사말 변형 3개. '내가 넣은 민원'의 진행을 묻는 말(조회)은 넣지 않음 | 문장마다 `bal-inq-NNN` |
| 거절 A4 | 155 | 잡담·상식 질문 36 × 3, 광고 10 × 3, 의미 없는 입력 20 | 문장마다 `bal-oos-NNN` |

보강 뒤 건수: 접수 2,025 / 조회 대상 있음 1,620 / 조회 대상 없음 640 / 문의 안내 609 / 접수(내용 없음) 600 / 거절 583 (합계 6,077)

학습할 때는 `records.pick_balanced()` 가 6종을 **같은 비율**로 고르므로(README "종류별 비율 맞추기"), 건수가 남는 접수·조회는
일부만 쓰이고 모자란 종류는 몇 번 반복됩니다. 보강은 그 반복을 줄이기 위한 것입니다.

## 과제 2·3. 민원 분석 JSON

입력은 앱과 같이 **민원 제목 + 개인정보를 가린 민원 원문**, 출력은 아래 JSON 하나입니다.

- 원문이 **1,500자를 넘으면 앞 1,500자만 넣고 `…(이하 생략)` 을 붙입니다.** 앱이 이렇게 잘라서 모델에 넘기므로
  (`prompts.analysis_content()`), 정답도 **잘린 원문만 보고** 만들어야 합니다. (뒷부분에만 있는 내용을 요약에 넣지 않음)
- 앱은 Ollama 구조화 출력(`prompts.ANALYSIS_JSON_SCHEMA`)으로 형식을 강제합니다. 정답 JSON 도 이 스키마를 만족해야 합니다.
  (8개 필드 모두 있음, `key_points` 1~3개, `keywords` 최대 5개, `category` 는 7종 중 하나)

| # | 필드 | 규칙 |
|---|---|---|
| C1 | (필드 구성) | `title`, `summary`, `key_points`, `urgency`, `needs_review`, `review_reason`, `category`, `keywords`. 모델이 스스로 적던 `confidence`, `reason` 은 **없앰** |
| C2 | `title` | 원문 표현을 쓴 짧은 명사형, 20자 이내 |
| C3 | `summary` | 2~3문장(원문이 한두 문장이면 1문장). "~라는 민원이다. ~를 요청했다." 형태. 원문에 없는 날짜·기관·장소·해결책은 넣지 않음. **요약에 쓴 숫자(금액·날짜·횟수 등)는 입력 제목이나 (잘린) 원문에 있는 숫자만** 씁니다 - 계산하거나 바꾼 숫자(예: 원문 "두 달"→요약 "60일", "두 번"→"주 2회", "혼자"→"1인")도 안 됩니다. `title`·`key_points` 도 같습니다. 원문에 없는 관계·의도를 짐작해 쓰지 않습니다("그냥 넘어가라"→"문제를 덮으려 한다" 금지) |
| C4 | `key_points` | 1~3개. 민원 대상, 문제 상태, 요청 사항 위주 |
| C5 | `category` | `categories.py` 7종 중 하나. 정의와 괄호 안 경계 규칙을 따름 |
| C6 | `keywords` | **원문에 글자 그대로 있는 명사** 3~5개. 원문이 짧아 명사가 모자라면 있는 만큼(1~2개)만 - 억지로 채우지 않음. **입력 제목은 원문이 아닙니다** - 제목에만 있는 표현(예: 제목 "운영시간", 원문 "운영 시간")은 쓰지 않고, 띄어쓰기까지 원문과 같게 씁니다 |
| C7 | `urgency` | `high`: 인명·안전 위험(화재, 가스, 붕괴, 추락, 교통사고 우려, 갇힘, 소방차 진입 불가, 폭염 속 작업·온열 질환 우려, 아동 방임·독거노인 연락 두절, 유해물질 노출 등). 실제 사고가 없어도 그런 위험을 알리면 high / `medium`: 생활 불편·행정 처리 지연·금전 피해, **이미 있는 시설·서비스의 고장·파손·부실·운영 문제**, 권리 침해(여권 압수 등 인명·안전이 아닌 것) / `low`: 단순 문의, 칭찬·감사, **지금 겪는 문제 없이** 새로 만들거나 늘려 달라는 제안 |
| C8 | `needs_review`, `review_reason` | 내용이 너무 짧아 무엇이 문제인지 모르거나, 대상·위치를 알 수 없거나, 여러 민원이 섞여 있으면 `true` 와 이유 한 문장("~가 원문에 없다."). 아니면 `false`, `null` |

**C8 의 "사업장을 알 수 없음" 기준**: 임금·근로조건·직장 내 괴롭힘·작업장 안전, 가맹·하청 같은 사업자 간 분쟁처럼 **특정 사업장·업체를 상대로 한 민원**인데
그 이름이 원문에 없거나 "OO산업"처럼 가려져 있으면 `true` ("회사 이름이 원문에 없다."). 지원 사업·제도처럼 행정기관을 상대로 한 민원은 `false`.

**C8 의 "위치를 알 수 없음" 기준**: 현장에 가서 조치해야 하는 민원(시설 파손, 위생, 소음, 안전, 특정 업소·사업장)인데
장소·건물·업소 이름이 원문에 없으면 `true` ("여기", "이 근처", "우리 아파트" 처럼 가리키기만 하는 말도 없는 것으로 봄).
행정 처리·제도·급여·홈페이지처럼 장소가 필요 없는 민원, 칭찬, 단순 문의는 위치가 없어도 `false` 입니다.

### 분석 데이터 구성 (v7 까지 407건 - v8 에서 284건 추가, 아래 "v8 데이터 정리" 참고)

PDF·HWP·CSV 일괄 접수는 LLM 을 거치지 않으므로, 앱에서 `analyze()` 에 들어오는 것은 **사람이 양식에 쓴 50~500자 민원**이 대부분입니다.
그래서 원문은 backend 데이터를 바탕으로 이 길이대로 만들거나 새로 쓰고, 앱에서 실제로 생기는 어려운 경우를 섞었습니다.

| 종류 (`tags` / `source`) | 건수 | 만드는 법 | id / group |
|---|---|---|---|
| `원문` | 74 | backend `접수` 문장 그대로 | `a-<backend id>` / backend group |
| `확장` | 92 | backend `접수` 문장을 2~5문장으로 늘림 - 경위·기간·시도한 조치·요청 사항을 덧붙이고 말투(구어체·공문형·경위 서술)를 바꿈 | `a-<backend id>-x` / **backend group 그대로** |
| `cases` | 25 | `cases.csv` 문장 그대로 | `a-case-<줄>` / `case-<줄>` |
| `source: new` | 216 | 앱에 들어올 법한 민원을 새로 씀. 아래 `긴원문`·`여러민원`·`문의·제안` 유형 포함 | `a-new-<분야>-<번호 또는 유형>` / id 와 같음 |

새로 쓴 민원 중 아래 유형은 태그로 표시했습니다. (건수는 위 표에 포함)

| 유형 (`tags`) | 건수 | 내용 |
|---|---|---|
| `긴원문` | 7 | 1,600~1,750자 공문형 민원 (카테고리별 1건). **1,500자 뒤에는 덧붙이는 말·별건·연락처만** 두고, 정답은 앞 1,500자만 보고 작성 |
| `여러민원` | 12 | 같은 분야 민원 여러 건이 한 글에 섞임. `needs_review=true`, key_points 에 각 민원 |
| `문의·제안` | 48 | 단순 문의·제안·칭찬 (`urgency=low`). 칭찬·감사는 카테고리 정의대로 **분야와 상관없이 `기타`** |

일부 레코드에는 아래 두 가지를 겹쳐 적용했습니다. (건수는 위 표에 포함)

| 겹친 처리 (`tags`) | 건수 | 내용 |
|---|---|---|
| `제목-문장형` / `제목-모호` | 95 / 44 | **입력 제목 섞기.** 앱의 '민원 제목' 칸은 챗봇이 채운 짧은 명사형일 수도, 사람이 쓴 문장형("~ 신고합니다")이나 내용 없는 제목("민원드립니다", "도와주세요")일 수도 있습니다. 섞어 넣어 모델이 제목을 베끼지 않고 **원문을 보고** 제목·카테고리를 정하게 합니다 |
| `개인정보가림` | 22 | 원문에 `[개인정보 제외]` (앱이 전화번호·이메일을 가린 모양)가 들어 있음. 정답에는 넣지 않음 |

- **카테고리는 backend(또는 cases.csv) 라벨을 그대로** 씁니다. 늘릴 때 카테고리가 바뀔 만한 내용을 넣지 않습니다.
- 확장 원문은 같은 group 이라 원래 문장과 같은 분할(학습/검증/평가)에 들어갑니다.
- 확장 원문에 장소·업소 이름을 넣으면 C8 이 `false` 가 될 수 있습니다. 원문마다 정답을 다시 판단합니다.
- `여러민원` 은 카테고리 판단이 흔들리지 않도록 같은 분야 민원끼리만 섞었습니다.
- **카테고리별 건수**: 기타 65, 나머지 6개 분야 57건씩. 칭찬·감사 13건이 모두 `기타` 라 기타가 조금 많습니다.
  학습할 때는 `records.pick_balanced()` 가 카테고리 비율을 같게 맞춥니다.
- **분할**: 대부분은 group 해시로 정하고, 일부 레코드에 `split` 을 지정해 카테고리마다 평가셋이 9~12건이 되게 맞췄습니다.
  (train 39~43 / val 7~10 / test 9~12, 전체 train 280 / val 57 / test 70. 평가 1건 = 약 1.4%p)

## v9 평가셋 보강 (test 전용, 학습·검증 데이터는 그대로)

평가 점수의 신뢰구간을 좁히려고 **test 분할에만** 레코드를 새로 넣었습니다. 모두 `"split": "test"` 로 고정했고 group 은 id 와 같으며,
