## 화면과 권한

1. 관리자 메뉴의 `삭제된 데이터`에서 통합 전체와 7개 부서 필터를 제공한다. 미분류 데이터가 있으면 별도 필터도 나타난다.
2. 목록에는 제목, `관리자 삭제`/`민원인 삭제`, 부서, 삭제 시각만 표시한다. `원본 내용 확인`을 펼칠 때 원문과 삭제 사유를 추가 조회한다. 기록이 없는 옛 데이터는 삭제 주체를 추측하지 않고 `삭제 주체 기록 없음`으로 표시한다.
3. 10·20·50·100건 서버 페이지 조회를 지원한다. 목록/건수는 5초마다 각각 갱신한다. 건수 조회 실패가 목록 조회 성공을 가리지 않는다.
4. 전체 부서 조회는 모든 관리자에게 허용한다. 다른 부서는 읽기 전용이며 복원/삭제 API도 담당 부서 외의 변경을 거부한다. 미분류는 부서가 있는 관리자가 처리할 수 있고 복원하면 그 관리자의 부서로 배정한다.
5. 체크박스로 개별/현재 페이지/여러 페이지의 데이터를 최대 1,000건 선택해 영구 삭제한다. 부서 필터 변경 시 선택을 비운다. `담당 부서 전체 영구 삭제`는 페이지와 무관하게 자신의 부서에 보관된 삭제 데이터만 제거한다.
6. 수동 영구 삭제는 되돌릴 수 없음 안내와 로그인 비밀번호 재입력을 요구한다. 요청 중 버튼을 비활성화하고 중복 전송을 막는다. 복원 후 목록/건수/부서 보관함도 갱신한다.

## 보관 한도 및 자동 정리

한도는 **모든 부서 합산 10,000건**으로 선택했다. 화면이 본문 전체를 한꺼번에 내려받지 않고 서버 페이지 조회/필요 시 원문 조회를 사용하며, 삭제 시각·부서 인덱스로 조회한다. 이는 요청 범위(5,000~30,000건) 내의 보수적인 건수 정책이며, 하드웨어별 메모리·디스크 최대 부하를 실측해 산정한 보장치는 아니다. 원문 길이에 따라 저장 용량은 달라진다.

사용자의 `가장 늦게 들어온 순`은 **삭제 보관함에 최근 들어온 순**으로 적용했다. 일반적인 오래된 순 보관 정책과 반대이므로 운영 적용 전에 반드시 확인한다.

| 조건 | 정리할 기존 보관 데이터 |
| --- | --- |
| 기존 건수 + 유입 건수 ≤ 10,000 | 정리하지 않음 |
| 한도 초과, 한 번에 1~100건 유입 | 최근 보관된 기존 100건 |
| 한도 초과, 한 번에 101건 이상 유입 | 최근 보관된 기존 데이터 중 유입 건수 +100건 |
| 기존부터 한도 초과/단일 유입 자체가 한도 초과 | 한도 이내가 되도록 추가 정리, 필요하면 신규 유입도 포함 |

예: 10,000건에 1건이 들어오면 기존 100건 정리 후 9,901건, 150건이 한 번에 들어오면 기존 250건 정리 후 9,900건이 된다. 유입 건수는 한 삭제 요청/트랜잭션에서 보관함으로 옮기는 수다. 여러 개별 요청을 미래까지 모아서 예측하지 않는다.

- 정렬은 `deleted_at DESC, id DESC`다. 활성 민원은 자동 정리 대상이 아니다. 한도는 부서별이 아닌 통합 보관함 기준이므로 자동 정리로 다른 부서의 삭제 데이터도 제거될 수 있다.
- 자동 정리는 이번 요청의 자동 보관 정책에 따라 비밀번호 없이 실행한다. 수동 영구 삭제의 비밀번호 확인과 별개다.
- 기록의 복구는 불가능하며 연결된 답변은 FK의 ON DELETE CASCADE에 따라 삭제된다. 원본 업로드 파일의 물리 파일까지 지우는 기능은 아니다.
- PostgreSQL advisory 트랜잭션 잠금으로 보관/복원/영구 삭제를 직렬화한다. 감사 로그에는 수행자 ID·건수·대상 ID/정책을 기록하며 민원 본문·비밀번호는 기록하지 않는다.

## 복원과 민원인 데이터 보호

삭제 주체가 관리자든 민원인이든 **관리자 보관함으로만** 복원한다.

- 기존 소유자는 `original_owner_user_id`에 보존하고 `owner_user_id`는 NULL로 분리한다.
- 민원인 목록/상세/검색/답변 조회의 소유자 조건에 걸리지 않으므로 민원인에게 다시 나타나지 않는다. 복원 뒤 새 답변을 작성해도 민원인에게 보내지지 않는다.
- 원본 제목·내용·기존 부서는 유지한다. 전송된 답변이 있거나 삭제 전 완료였다면 완료로 유지하고, 아니면 접수 대기로 복원한다. 미분류는 복원 관리자의 부서로 배정한다.
- 분류가 진행 중 삭제/복원되면 `analysis_revision` 증가와 조건부 갱신으로 오래된 분류 결과를 버린다. 취소 사유·삭제 주체는 보관 중 표시하고 복원 이벤트에는 감사 이력을 남긴다.
- 관리자 취소 직후에는 기존 민원인 화면의 취소 사유 안내를 유지한다. 관리자 전용 복원 이후에는 그 안내도 민원인 목록에서 사라진다.

## DB 적용 및 주요 파일

- `database/migrations/20261019_trash_archive.sql`: 반복 가능한 추가형 이전. 기존 취소 민원 보관함 편입, 3개 컬럼과 2개 부분 인덱스. 영구 삭제나 계정 재생성 없음.
- `database/init.sql`: 새 DB 전체 초기화 시 위 컬럼/인덱스 포함. **기존 DB 업데이트에 실행하면 기존 데이터가 지워지므로 사용하지 않는다.**
- `app/services/trash.py`: 보관/복원/자동 한도/비밀번호 확인/영구 삭제/감사 기록.
- `app/routers/trash.py`: 관리자 전용 조회·변경 API. 기존 catch-all 라우터보다 먼저 등록해야 한다.
- `app/routers/complaints.py`: 민원인/관리자의 취소 경로를 동일 보관 서비스로 연결, 기존 복원/영구 삭제 API도 같은 권한 적용.
- `frontend/src/DeletedData.jsx`, `deletedData.css`: 독립 보관함 화면과 비밀번호 확인 창. 650px 이하에서는 부서 필터 2열, 행별 버튼 세로 배치.

추가 환경 변수는 없다. 기존 DATABASE_URL을 사용한다. 앱 계정에는 ALTER TABLE/CREATE INDEX와 기존 조회/변경 권한이 필요하다. 팀원이 원래 폴더 구조를 유지한 채 코드를 받고 부서 ID 이전 후 FastAPI를 재시작하면 추가형 이전이 적용된다.

## API 계약

| API | 역할 |
| --- | --- |
| GET /api/trash/counts | 전체/미분류/7개 부서 건수와 보관 정책 |
| GET /api/trash/items | department_id 또는 unassigned, limit(1~100), offset으로 제목 목록 조회 |
| GET /api/trash/{id} | 삭제 원문·사유 필요 시 조회 |
| POST /api/trash/{id}/restore | 담당 부서/미분류만 관리자 전용 복원 |
| POST /api/trash/permanent | ids(1~1,000개), password로 선택 영구 삭제 |
| POST /api/trash/department/{id}/permanent | password로 담당 부서의 삭제 데이터 전체 영구 삭제 |

일반 사용자에게는 모두 403을 반환한다. 선택에 이미 복원/삭제된 ID가 포함되면 409, 다른 부서가 포함되면 403으로 전체 요청을 취소한다. 과거 전 부서 테스트 삭제 예외는 비활성 상태를 유지한다.

## 같은 날 UI 보완

삭제 보관함이 독립 화면으로 분리되면서 기존 `.grid`/`.list`의 버튼 스타일을 받지 못해 기본 회색 버튼으로 표시되던 문제를 수정했다. 부서 필터는 분류 목록의 `.grid`를 공유하며 기본 3열, 기존 공통 900px 이하 기준에서는 2열이다. 담당 부서 하늘색/선택 부서 파란색 테두리, 왼쪽 건수 표시, 둥근 모서리를 동일하게 사용한다. 선택 삭제 도구·개별 복원/영구 삭제·비밀번호 확인창 버튼에도 삭제 보관함 내부로 한정한 스타일과 키보드 포커스/비활성 상태를 적용했다. 420px 이하에서는 패딩과 선택 도구 버튼 폭을 조정한다. 백엔드·권한·보관 정책은 변경하지 않았다.

실제 CSS 소스를 로드하는 스타일 회귀 테스트 2개를 추가해 공통 스타일과 함께 로드돼도 담당 부서/선택 색상, 둥근 버튼, 삭제 경고색, 선택 전 비활성 상태가 유지되는지 검증한다.

## 검증 및 남은 주의점

검증은 별도 임시 PostgreSQL DB에서 실행했고 테스트 후 DB를 제거했다. 실제 앱 DB의 기존 144건은 보존했다. 이전에 취소 상태였지만 삭제 시각이 없던 1건만 보관함으로 편입했고 실제 데이터의 복원/영구 삭제는 실행하지 않았다.

- 보관함 백엔드 16개: 양측 삭제 원문 보존, 7개 부서 조회/권한, 소유자 분리 복원, 완료 답변 보존, 잘못된 비밀번호, 선택 삭제 원자성, 부서 삭제 범위, 10,000건 한도, 150건/초대량 유입, 동시 요청, 분류-삭제-복원 경쟁, 반복 이전.
- 관련 기존 백엔드 회귀 48개: 부서 권한 11, 가져오기 파이프라인 15, 파일 추출 10, 조회 필터 8, 워커 관리 4.
- 프론트엔드 관련 59개: 신규 보관함 10개 및 기존 부서 권한/민원 화면/선택 조회/민원 도구 테스트. 프로덕션 빌드 성공.
- 직접 브라우저 확인은 해당 로컬 주소의 브라우저 접근 승인이 거절되어 진행하지 않았다. 자동화된 컴포넌트 테스트와 빌드 검증을 수행했으며 시각 검증 완료로 간주하지 않는다.
- 전체 init-schema 검증 9개 중 3개는 기존 부서 통합/계정 seed 기대값 불일치로 실패한다. 새 보관함 컬럼/인덱스를 제외한 이전 기준으로도 동일 3개 실패를 재현했다. 이 업데이트에서 관련 계정·통합 로직을 임의 수정하지 않았다. 관련 6개 스키마 검증은 통과했지만 전체 프로젝트 테스트가 모두 통과한 것은 아니다.
- 10,000건의 매우 긴 원문/답변/벡터에 대한 장시간 부하·실제 디스크 회수량 측정은 하지 않았다. PostgreSQL은 DELETE 후 내부 공간을 재사용하며 파일 크기가 즉시 줄어드는 것은 아니다. 운영에서는 autovacuum/디스크 사용량을 함께 관찰해야 한다.
