# 8,192토큰 적용과 문서 분할 사전 점검

## 이번에 적용한 범위

사용자 요청에 따라 공통 임베딩 요청의 `num_ctx`와 `num_batch`를 모두 8,192로 올렸다.
실제 `.env`, 설정 기본값, `.env.example`을 맞추고 백엔드와 RAG 워커를 재시작했다.
모델은 기존 `bge-m3:latest`, 1,024차원이며 DB 접속·RAG 검색·채팅 프롬프트는 그대로다.
관련 임베딩 테스트 2개가 통과했다. 기존에 길이 초과였던 4,653토큰 본문을 실제
모델로 요청해 유효한 1,024차원 벡터를 받았고 Ollama의 실행 컨텍스트도 8,192다.
두 AI 서버(11434/8080)와 백엔드·DB(8000)의 상태 확인은 모두 HTTP 200이다.

문서 분할·조각 저장·검색 변경은 적용하지 않았다.
8,192토큰을 넘는 행은 현재처럼 제외 사유를 기록하고 다음 행으로 진행한다.
이전 업로드 작업은 이미 취소돼 있었다. 1,800건 처리·820건 저장·980건 제외 상태를
보존했으며 재개하지 않았다. 한도 상향이 과거 제외 자료를 자동으로 다시 넣지는 않는다.

## 현재 구조에서 확인한 문제

### 1. 조항의 일부만 전달돼 의미가 달라질 수 있다

`app/agent.py`의 `aiFAQ`는 벡터 거리가 가까운 3행을 골라 각 본문의 앞 5,000자만
반환한다. 제목, 문서 ID, 조항 번호, 시행일 같은 메타데이터는 결과에 넣지 않는다.
부모 문서나 앞뒤 조각을 추가 조회하는 기능도 없다.

따라서 본문을 잘라 별도 행으로 넣기만 하면 일반 규정은 검색되고 예외·정의·참조 조항은
누락될 수 있다. 같은 법령의 조각이 상위 3건을 모두 차지해 다른 근거를 놓칠 수도 있다.
같은 문제는 현재 긴 문서의 관련 조항이 5,000자 이후에 있을 때도 발생할 수 있다.

조문·항·문단 경계를 유지하고 법령명·조항·버전을 전달해야 한다.
필요할 때 인접 조각 및 참조 조항을 다시 조회해야 하며, 단순한 일부 겹침만으로
멀리 떨어진 참조 조항까지 보장할 수는 없다.

### 2. 저장된 연관성을 검색 단계에서 사용해야 한다

현재 CSV 가져오기는 업로드 작업마다 하나의 `document_id`를 만든다.
`department_documents.id`는 원본 CSV 행마다 고유하지만, `document_id`는 파일 전체가 공유한다.
확인 당시 820개 서로 다른 제목의 저장 자료가 같은 `document_id` 하나를 사용했다.
`version`에는 법령 개정 버전이 아닌 CSV 행의 순번이 들어간다.

따라서 기존 `document_id`만 재사용해 조각을 넣으면 어느 법령의 어느 조각인지 구분할 수 없다.
현재 검색도 ID를 반환하거나 관계를 따라가지 않으므로 관계 정보가 자동으로 전달되지 않는다.

DB에는 별도 `rag_documents` 9건과 `rag_chunks` 57건도 있다. 이 두 테이블은
문서 외래키·조각 순서 등의 구조를 갖지만, 현재 등록된 `/api/chat` → `aiFAQ` 경로는
`department_documents`만 조회한다. 별도 `rag.py` 코드와 테이블이 존재하는 것으로
현재 CSV 자료의 부모·자식 연결이 자동 제공되는 것은 아니다. 기존 자료는 변경하지 않았다.

## 향후 구현 시 필요한 설계 — 아직 미적용

- `department_documents`에 법령별 원문 전체와 고유 ID를 보존한다.
- 조각 저장 구조는 원문 ID를 외래키로 참조한다. 조각 순서·원문 내 위치·조항·벡터를 저장한다.
  기존 `rag_chunks` 구조를 재사용할지 별도 구조가 필요한지는 현재 원문 테이블과의 연결을
  먼저 설계해야 하며, 이름이 같은 목적이라는 이유만으로 기존 자료를 섞지 않는다.
- 조각 본문은 원문 일부 그대로 유지한다. 분할 과정에서 법령을 요약·재작성하지 않는다.
- 가능한 경우 법령 식별자와 시행일·개정 버전을 함께 보관한다.
- 검색은 적합한 조각을 찾은 후 원문 연결과 필요한 주변/참조 조항을 이용해 답변 근거를 구성한다.
- 중복 판정은 원문 전체를 기준으로 유지한다. 서로 다른 법령에서 같은 조각 문구가 나와도
  원문과의 연결이 사라지지 않도록 조각별 중복 제거와 구분한다.
- 삭제·복원·재업로드·개정 자료 교체 시 원문과 조각이 함께 일관되게 동작해야 한다.

검증에는 일반 규정과 예외가 다른 조각에 있는 질문, 다른 법령의 동일 조항 번호,
멀리 떨어진 정의·준용 조항, 개정 전후 규정, 분할 전후 원문 일치가 필요하다.
모든 조각을 매번 통째로 LLM에 보내면 컨텍스트 제한이 다시 생기므로 필요한 근거를 선택해야 한다.

원문을 부모로 보존하고 조각을 연결하는 방식은 일반적인
[부모·자식 색인 구조](https://learn.microsoft.com/en-us/azure/search/search-how-to-define-index-projections)와 같다.
분할 경계와 문맥 유지에 대해서는
[문서 분할 안내](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents)를 참조했다.
