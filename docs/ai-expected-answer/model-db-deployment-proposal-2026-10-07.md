# AI 예상 답변: 모델·DB·배치 제안

검토 기준일: 2026-10-07. 현재 프로젝트 코드와 제작자·공식 서버 문서를 기준으로 작성했다. 아래는 설계 제안이며 모델 설치·다운로드, DB 변경, 배포, 한국어 민원 성능 실측은 수행하지 않았다.

## 1. 추천 조합

초기 조합은 **Qwen3-Embedding-0.6B + PostgreSQL/pgvector + Qwen3-Reranker-0.6B + Qwen3.5-4B**로 제안한다. Laya Multilingual은 민원 분류 평가 후 추가할 선택 구성이다. 한국어 법령 검색·민원 답변 정확도가 이미 검증된 조합이라는 의미는 아니다.

| 역할 | 모델/기술 | 제안 목적 |
| --- | --- | --- |
| 민원 분류 | Laya Multilingual, 검증 후 도입 | 6개 부서와 부서별 세부 유형의 후보 선택 |
| 임베딩 | [Qwen/Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B) | 질의·공식 자료를 같은 1024차원 공간에서 검색 |
| 재정렬 | [Qwen/Qwen3-Reranker-0.6B](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B) | 검색 후보를 민원과의 관련성으로 재평가 |
| 기본 답변 | [Qwen/Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B) | 검색 근거를 이용한 한국어 예상 답변 생성의 초기 후보 |
| 답변 비교 후보 | [Qwen/Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B) | 4B와 같은 자료·질문으로 정확도와 지연을 비교 |
| 검색 저장소 | [PostgreSQL + pgvector](https://github.com/pgvector/pgvector) | 계정·민원·공식 자료 메타데이터와 벡터 검색 통합 |

Qwen3-Embedding-0.6B는 제작자 설명상 다국어 모델이며 최대 1024차원을 지원한다. 지시문은 질의에 맞춰 적용하고, 문서 입력·질의 입력의 형식과 정규화 방식을 고정한다. 비교 대상으로 [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3)의 1024차원 검색도 같은 검증 자료로 평가한다. 두 모델의 차원이 같아도 벡터를 섞어 검색하지 않는다.

Qwen3.5-4B는 작은 기본 생성 모델 후보로 선택했다. 9B 채택 여부는 복합 민원·예외 조건·지역/시점 구분을 포함한 평가에서 개선 폭이 실제로 확인되는지로 결정한다. 파라미터 수나 다국어 지원 표기만으로 한국어 법률 답변의 우수성을 단정하지 않는다.

여러 생성 모델을 모든 요청마다 호출하기보다, 분류·검색·재정렬을 담당하는 작은 모델과 생성 모델 하나를 조합한다. 이후 9B가 필요한 요청을 별도로 식별할 근거가 생기면 단계적 호출을 추가한다. 근거 부족은 큰 LLM 재호출만으로 해결되지 않으므로 추가 자료 검색·확인 질문이 먼저 필요할 수 있다.

## 2. 현재 프로젝트에서 확인한 제약

| 확인 사항 | 위치 | 의미 |
| --- | --- | --- |
| PostgreSQL 16 + pgvector 이미지 | docker-compose.yml | 벡터 DB를 새 제품으로 교체하지 않고 시작 가능 |
| 민원 벡터 1536차원 | database/init.sql:47 | 기존 민원 검색 인덱스 |
| 부서 문서 벡터 1536차원 | database/init.sql:180 | 문서 전체에 벡터 하나가 있는 현재 구조 |
| 1536차원 요청·검사·절단 | complaintai-react-fastapi/app/ai.py:119 | 1024차원 모델은 현재 함수에서 저장용 벡터를 반환하지 못함 |
| 분류·CSV 분석에 공통 LLM 설정 사용 | complaintai-react-fastapi/app/settings.py:24 | 답변용 모델 설정은 별도 도입하는 편이 적합 |
| 기존 모델명·차원 일부 하드코딩 | complaintai-react-fastapi/app/main.py:510, 586 | 환경변수만 바꾸는 것으로 모델 전환이 끝나지 않음 |
| GPU | 로컬 nvidia-smi 확인 | NVIDIA GeForce GTX 1060 3GB |
| CPU | 로컬 레지스트리 확인 | Intel Core i5-6500 3.20GHz |
| RAM | 확인하지 못함 | 로컬 모델 실행 용량은 추가 확인 필요 |

추천한 0.6B 임베딩의 1024차원은 기존 1536차원 경로와 호환되지 않는다. **공식 자료 검색용 1024차원 테이블과 임베딩 함수를 별도로 추가**하는 안을 제안한다. 기존 민원 벡터의 보존·전환은 별도 마이그레이션 문제다.

현재 GTX 1060은 NVIDIA 공식 표에서 compute capability 6.1로 분류된다. 현재 vLLM GPU 설치 문서는 NVIDIA 7.5 이상과 Linux를 요구하고 Windows 네이티브를 지원하지 않는다. 따라서 이 PC의 GPU에 vLLM 운영 구성을 배치하는 안은 적합하지 않다. [NVIDIA 지원 표](https://developer.nvidia.com/cuda/gpus/legacy), [vLLM 설치 요구사항](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/).

Ollama의 qwen3.5:4b 게시 패키지는 현재 약 4.0GB이며, 모델 가중치 항목은 약 3.3GB다. 이는 실행 중 메모리 전체가 아니며, 현재 3GB GPU에 완전히 상주시킬 수 있는 크기가 아니다. CPU 또는 부분 GPU 실행은 호환성과 RAM을 확인한 후 시험해야 한다. [Ollama 모델 패키지](https://ollama.com/library/qwen3.5:4b).

## 3. DB와 원문 저장

초기에는 **PostgreSQL 한 개에 pgvector를 추가한 구성**을 유지한다. 공식 자료의 벡터와 시점·지역·발행기관을 같은 질의에서 처리할 수 있다. 원본 PDF/HWPX는 개발 시 파일 저장소, 서비스 확장 시 객체 저장소에 두고 DB에는 원문 경로·해시·추출 텍스트를 저장한다.

| 논리 테이블 | 저장 내용 |
| --- | --- |
| knowledge_sources | 공식 URL, 자료 종류, 발행기관, 공개/검토 상태 |
| knowledge_documents | 출처별 판본, 원문 경로·해시, 발행일·적용일·지역 |
| knowledge_chunks | 조문/문단별 텍스트, 쪽수, 부서·유형, 문서 판본 연결, vector(1024) |
| ai_expected_answers | 요청자, 질의, 생성 결과, 생성 모델·프롬프트 버전 |
| ai_answer_citations | 답변에 실제 사용한 문서 판본·문단·조문·쪽수 |
| knowledge_import_jobs | 원문 처리·임베딩·색인 작업 상태와 오류 |
| embedding_profiles | 모델 ID·revision·차원·입력 지시문·정규화·실행 판본 |

knowledge_chunks에 cosine 거리용 HNSW 인덱스를 고려한다. 작은 자료 집합에서는 먼저 정확 검색을 기준으로 삼고, HNSW 사용 시 부서·지역·시행일 필터를 적용한 검색의 누락을 측정한다. pgvector 0.8.0부터의 iterative scan 또는 적합한 인덱스 구성을 검토한다. 현재 DB에 설치된 확장 버전은 이번 작업에서 확인하지 않았다. [pgvector 검색·필터 문서](https://github.com/pgvector/pgvector).

법령명·조문번호는 구조화된 필드로 정확 매칭하고, 핵심어 검색과 의미 벡터 검색의 후보를 합친다. 문자열 검색 보조에는 PostgreSQL의 [pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html)을 고려한다. 한국어 조사·복합어 처리를 일반 영어 검색 설정으로 대신하지 않고, 필요하면 한국어 전처리와 검색 평가를 추가한다.

LLM만 교체하면 문서 임베딩을 다시 만들 필요는 없다. 임베딩 모델·공간을 교체하면 새 인덱스로 재임베딩한다. 실행 엔진·양자화·지시문 변경도 검증 후 색인 판본을 전환한다.

## 4. 임베딩 생성과 실시간 답변을 분리

### 자료 등록·변경 시

1. 원문 확보 및 공식 출처·판본 확인.
2. PDF/HWPX 텍스트 추출, 필요한 경우 OCR.
3. 법령은 조문·항·호, 매뉴얼은 제목·문단 기준으로 분할.
4. 초기 분할 목표는 약 300~600 모델 토큰. 예외·조건이 분리되지 않도록 실제 문서 구조에 맞춰 조정.
5. 모델로 배치 임베딩하고 새 판본의 색인을 구성.
6. 검색 결과를 검증한 후 해당 판본을 서비스에 반영.

문서가 변경되지 않으면 매 요청마다 문서를 다시 임베딩하지 않는다. 학습되지 않은 모델도 이 검색 색인을 구축할 수 있다. 법령 개정은 기본적으로 원문·메타데이터·검색 색인 갱신으로 반영한다.

### 민원 입력 시

1. 민원 분류와 부족한 정보 확인. Laya는 검증 후 이 단계에 사용.
2. 민원 질의를 같은 임베딩 프로필로 벡터화.
3. 해당 지역·적용 시점·자료 검토 상태를 반영해 의미 검색과 정확/핵심어 검색 수행.
4. 초기 설정으로 통합 후보 약 30개를 얻고, 상위 약 16개를 재정렬.
5. 중복을 줄인 근거 약 5~8개를 생성 모델에 전달.
6. 근거에 따른 예상 답변, 확인할 사항, 처리 절차, 인용 자료를 생성.
7. 답변의 출처 ID가 실제 검색 자료와 일치하는지 검사하고 판본까지 저장.

후보 수와 토큰 길이는 제안 시작값이며 실측으로 조정한다. 부서 분류가 불확실하거나 여러 쟁점이 있으면 관련 부서와 공통 법령도 검색한다. 사례의 결론, FAQ, 내부 매뉴얼과 법령의 효력을 구분해 답변한다.

## 5. 모델 실행 위치와 방식

웹 요청을 받는 FastAPI와 모델 추론 프로세스를 분리한다. 추론 서비스는 시작할 때 모델을 적재해 유지하고, FastAPI는 HTTP API로 호출한다. 웹 워커마다 GPU 모델을 따로 적재하는 구성을 피하고, 작업별 동시 실행 수를 제한한다.

| 단계 | 웹·DB | 임베딩/재정렬 | 생성 LLM |
| --- | --- | --- | --- |
| 현재 PC에서 기능 개발 | 현재 React·FastAPI·PostgreSQL 유지 | CPU 또는 별도 모델 서버 | Ollama에서 CPU/부분 GPU 실험; 빠른 응답 성능은 미확인 |
| 별도 GPU 서버를 이용한 MVP | 현재 PC 또는 CPU 서버 | CPU 전용 프로세스나 GPU 서버의 예약 자원 | GPU 서버에 4B 모델을 상주시키고 API 호출 |
| 동시 이용자 증가 | 웹/DB와 추론 서버 분리 | TEI 임베딩 서비스·전용 재정렬 서비스 | Linux GPU 서버의 vLLM으로 생성 요청 처리 |

개발 환경에서 Ollama는 기존 코드의 /api/embed, /api/chat 연동을 재사용하기 쉬운 선택이다. 모델 태그 예시는 qwen3-embedding:0.6b와 qwen3.5:4b다. [Ollama 임베딩 모델](https://ollama.com/library/qwen3-embedding), [임베딩 API](https://docs.ollama.com/api/embed), [채팅 API](https://docs.ollama.com/api/chat).

서비스 환경의 임베딩 서버에는 **Hugging Face TEI**를 제안한다. 공식 지원 목록에 Qwen3-Embedding-0.6B가 포함된다. [TEI 모델·하드웨어 지원](https://huggingface.co/docs/text-embeddings-inference/supported_models).

Qwen 재정렬 모델은 공개 예제에 맞춘 Transformers 추론 서비스로 분리하는 안이 명확하다. TEI의 임베딩 지원이 곧 해당 재정렬 모델의 API 호환을 뜻하지는 않는다. 모델별 지원을 검증하고 배치 크기·입력 길이를 제한한다.

생성 서버에는 **vLLM**을 제안한다. Qwen 공식 카드의 텍스트 전용 실행 옵션을 적용하고, 처음에는 입력 문맥을 약 8K 토큰으로 제한해 평가한다. 빠른 기본 답변에는 thinking을 명시적으로 끄고 출력 길이를 제한한다. 설정 위치는 엔진별로 다르다: vLLM 계열 API는 chat_template_kwargs.enable_thinking, Ollama는 모델의 /api/show 지원 확인 후 think 파라미터를 사용한다. [Qwen3.5 사용 안내](https://huggingface.co/Qwen/Qwen3.5-4B), [Ollama think 설정](https://docs.ollama.com/api/chat).

서버 자원 계획은 다음처럼 시작하되, 수치들은 실제 용량 보장이 아닌 시험 목표다.

- 4B 생성 서버: 호환되는 현대 GPU의 VRAM 16~24GB를 후보로 두고, 문맥 8K·낮은 동시성에서 측정. 임베딩/재정렬은 CPU로 분리하거나 GPU 사용량을 명시적으로 예약.
- 9B 비교·확장 서버: 24GB급 GPU와 검증된 양자화 또는 적절한 정밀도를 비교. BF16 가중치·문맥 메모리·다른 모델 상주량을 합산해 설정.
- 같은 GPU에서 여러 서버를 띄울 때 각 서버가 VRAM 대부분을 예약하는 기본값을 함께 사용하지 않음. 전체 메모리 예산과 최대 동시 요청을 배포 구성에 명시.
- 현재 PC는 소규모 기능 개발에 활용하고, 빠른 다중 사용자 응답의 목표 성능은 GPU 서버에서 측정.

Redis는 초기 필수 구성으로 두지 않는다. PostgreSQL 기반 지식 등록 작업 관리로 시작하고, 큐·캐시가 실제 병목이 되면 별도 도입한다. Colab은 모델 비교·미세조정 실험에 사용하고, 서비스 요청을 받는 추론 서버는 상주 프로세스로 운영한다.

## 6. 도입 순서와 채택 기준

1. 1024차원 공식 자료 검색 경로와 모델 설정을 분리.
2. 소수의 원문 확인된 자료로 임베딩·정확/핵심어 검색·인용 연결을 구축.
3. 같은 자료와 질문으로 Qwen 임베딩 0.6B와 BGE-M3를 비교.
4. Qwen3.5-4B와 9B의 한국어 답변·인용·예외 조건·지역/시점 정확도 비교.
5. 재정렬을 추가했을 때 검색 개선과 지연 증가를 함께 측정.
6. Laya는 6부서·세부 유형 분류 정확도와 보정 성능을 측정한 후 추가.
