# AI 추천 답변 RAG 구현

2026-10-07. React·FastAPI 프로젝트의 민원인 기능에 추가했다.

## 사용자 흐름

- 왼쪽 `새 민원`, `작성한 민원` 아래 `AI 추천 답변`을 선택한다.
- 기본 화면은 채팅이다. 하단에 질문을 입력하면 내 메시지는 오른쪽, AI 답변은 왼쪽 말풍선으로 누적된다. Enter로 전송하고 Shift+Enter로 줄바꿈하며 한국어 입력 조합 중 Enter는 전송하지 않는다.
- 상단 `옵션`에서 `새 대화 시작`, `새로운 민원 작성하기`, `작성된 민원에서 선택하기`, `이용 안내`를 연다.
- `새로운 민원 작성하기`: 옵션에서 제목·내용 입력 폼을 열어 새 대화를 시작한다. 기본 채팅에서는 첫 질문에서 제목을 자동으로 만든다. 실제 민원 접수는 생성하지 않는다.
- `작성된 민원에서 선택하기`: 기존 내 민원 목록으로 이동한다. `이 민원 선택`을 누르면 추천 답변 화면으로 돌아와 해당 원문으로 새 대화를 자동 실행한다. 서버가 본인 소유 민원 원문을 읽으며 기존 민원 상태를 변경하지 않는다. 완료 민원도 선택할 수 있고 취소 민원은 제외한다.
- 답변 생성 상태는 AI 말풍선에 표시한다. 확인할 사항, 다음 절차, 공식 원문 링크와 근거 문단은 각 답변의 `답변 옵션`을 펼쳐 확인한다.
- 후속 질문은 완료된 본인 추천 작업의 ID로 연결한다. 서버가 원래 민원과 최근 대화 일부를 읽고 질문마다 공식 자료를 다시 검색한다. 이전 AI 답변은 공식 근거로 취급하지 않으며 검색 질의에는 이전 사용자 설명만 추가한다.
- 다른 메뉴로 이동하면 화면 대화가 유지된다. 새로고침·로그아웃·새 대화 시작 시 화면 기록은 초기화된다. DB에 저장한 추천 작업을 자동으로 불러오는 대화 목록 기능은 현재 제공하지 않는다.
- 근거 부족과 모델 장애를 구분한다. 장애를 성공 답변이나 임의의 모의 답변으로 대체하지 않는다.

## 실행 구조

`민원 입력 → Qwen3-Embedding-0.6B → PostgreSQL/pgvector 의미 검색 + 핵심어 검색 → Qwen3-Reranker-0.6B → Qwen3.5-4B → 출처 번호 검사 → 답변 저장`

기존 민원·부서 문서의 1536차원 벡터는 보존한다. 새 지식 테이블은 정규화된 1024차원이며 임베딩 모델 digest·질의 지시문·차원을 묶은 프로필로 분리한다. 프로필이 다른 벡터는 검색하지 않는다.

작은 초기 corpus에는 필터 후 정확 코사인 검색을 사용한다. HNSW 인덱스는 추가했지만 ANN 전환은 자료 규모와 검색 누락을 측정한 후 한다. 의미 검색과 핵심어 후보는 RRF로 합친다. 재정렬 점수 기준은 평가로 조정하는 설정값이며 정확도나 보정된 신뢰 확률이 아니다.

FastAPI 웹 서버와 CPU 재정렬 모델 프로세스는 분리한다. 생성·임베딩은 Ollama API를 사용한다. 재정렬은 제작자의 yes/no 마지막 토큰 로짓 계산을 사용하며 불필요한 전체 토큰 출력 로짓을 만들지 않는다.

`data/rag/official-pilot/`에 공식 응답 원본 HTML, 추출 문답 JSON, 해시·확인 시각·유형·판본·수집 한계가 있는 manifest를 저장한다. **32개 민원 유형 전체를 지원하는 법령·매뉴얼 corpus가 아니다.** `verified`는 공식 원문 답변 영역을 확인·추출했다는 의미이며 법률 전문가의 검토 완료를 뜻하지 않는다. FAQ의 법령 인용은 원문 법령 전체의 현행성 검증을 대신하지 않는다.

현재 검색은 전국 공통 자료만 사용한다. 지역 조례·사업을 추가하려면 지역 입력·일치 필터와 판본 검토를 함께 구현한다. 발행일과 법적 시행일은 구분하며 확인되지 않은 시행일을 임의로 채우지 않는다. 기존 7부서 업무 분류·계정은 유지하고, RAG 자료에는 조사한 6부서·32유형 메타데이터를 별도로 붙인다.

국민콜110 페이지에는 공공누리 출처표시·상업적이용금지·변경금지 조건이 표시되어 있다. 자료는 내부 개발·검증용으로 보존하며 외부 서비스 사용 전 이용 조건과 생성 답변 활용 범위를 확인한다. 이용 조건은 manifest에 기록했다.

## 최초 준비

PostgreSQL이 실행 중이어야 한다. 기존 DB에는 `database/init.sql`을 실행하지 않는다. FastAPI 시작 또는 지식 import 시 추가 마이그레이션 `database/migrations/20261007_ai_recommendations.sql`이 멱등적으로 적용된다.

```powershell
cd complaintai-react-fastapi
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
ollama pull qwen3-embedding:0.6b
ollama pull qwen3.5:4b

# 별도 Python 3.12 재정렬 환경
py -3.12 -m venv .rag-venv
.\.rag-venv\Scripts\python.exe -m pip install torch --index-url https://download.pytorch.org/whl/cpu
.\.rag-venv\Scripts\python.exe -m pip install -r requirements-reranker.txt
```

이 PC에서는 번들된 Python 3.12로 `.rag-venv`를 만들었다. `py -3.12`가 없으면 설치된 Python 3.12 실행 파일로 대체한다. 웹 환경은 기존 Python 3.14 `.venv`이며 Torch를 적재하지 않는다.

## 실행

```powershell
# 터미널 1: 재정렬 서비스
.\scripts\start_rag_reranker.ps1

# 터미널 2: 웹 API와 빌드된 React
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 개발 UI가 필요한 경우
cd frontend
npm install
npm run dev -- --host 127.0.0.1
```

개발 UI의 `/api`는 8000으로 프록시한다. 빌드 UI는 `http://127.0.0.1:8000`이다. `.env.example`의 `RAG_*` 설정을 참고한다. GTX 1060 3GB/메모리 약 16GB 환경에서는 CPU와 GPU 일부 사용 때문에 응답이 오래 걸릴 수 있다.

요청은 HTTP 202로 작업을 만들고 화면에서 진행 단계를 조회한다. 단일 웹 프로세스에 동시성 1, 사용자당 대기·진행 요청 최대 2를 적용했다. 서버 재시작 시 중단된 작업은 실패로 표시하고 다시 시도한다. 다중 웹 프로세스 운영 전 별도 작업 lease/worker를 도입해야 한다.

후속 질문은 `POST /api/ai-recommendations`에 `parent_recommendation_id`와 `content`를 보낸다. 부모 작업은 완료 상태·본인 소유여야 한다. 서버가 제목과 기존 민원 연결을 이어받고 대화 snapshot을 `conversation`에 저장한다. 최대 6개 대화 항목·4,000자로 맥락을 제한하며, 원래 사용자 설명을 우선 보존하고 최근 항목을 포함한다. 모든 대화 내용을 무제한으로 기억하지 않는다. 초기 채팅 입력은 4,000자, 옵션의 민원 내용 폼은 기존 12,000자 제한이다.

## 원문 수집·색인 갱신

```powershell
.\.venv\Scripts\python.exe scripts/fetch_rag_sources.py
.\.venv\Scripts\python.exe scripts/import_rag_knowledge.py data/rag/official-pilot/manifest.json
```

원문 확보 오류가 있는 자료는 건너뛰며 목록 페이지를 대신 색인하지 않는다. source ID, 공식 URL, 파일 해시, 확인 상태를 검사하고 전체 임베딩이 끝난 문서 판본을 트랜잭션으로 게시한다. 같은 본문·프로필은 건너뛴다. 이전 답변은 당시 근거 문단과 출처 판본을 snapshot으로 보존한다.

다른 원문은 manifest의 `documents`에 출처·원본 파일·검토 상태를 기록하고 `sections_path` 파일에 `heading`, `text`, `locator`를 넣어 import한다. 공식 원문과 비교한 뒤 verified로 게시한다. PDF/HWPX는 추출·구조 확인 후 이 형식으로 넣는다.

## 검증 및 학습 판단

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
cd frontend
npm test
npm run build
cd ..
.\.venv\Scripts\python.exe scripts/evaluate_rag.py --output ../docs/ai-expected-answer/rag-evaluation-2026-10-07.json
```

API·UI 테스트는 명시적인 모델 test double로 화면·권한·저장 동작을 검증한다. `evaluate_rag.py`는 실제 세 모델을 호출해 예상 출처·응답 상태·핵심어를 확인한다. 자동 통과는 법률 답변 정확도 인증이 아니며 원문 대조와 별도 검토가 필요하다. 출력에는 답변과 근거 원문을 보존한다.

- 자료가 없어 실패하면 공식 원문을 보강한다.
- 자료는 있으나 검색에서 놓치면 분할·질의·검색 후보를 점검하고 질문/정답 문단/헷갈리는 오답 문단으로 임베딩·재정렬 학습을 검토한다.
- 올바른 근거를 찾고도 답변에 없는 내용을 추가하면 검토된 민원/근거/답변 쌍으로 생성 모델 학습을 검토한다.
- 지연 문제는 추론 설정과 실행 장비를 개선한다.

법령 문서를 그대로 추가 학습하는 것으로 이 문제들을 구분 없이 해결하지 않는다.

이번 최종 실제 API 평가에서는 9건 모두 처리가 완료됐고 단순 자동 기준 7건이 통과했다. 원문 대조에서 조건 생략과 복합 질문 누락이 남아 **Qwen3.5-4B 추가 학습이 필요하다고 판단했으며 아직 학습은 수행하지 않았다.** 임베딩·재정렬은 관련 원문을 찾았다. 세부 결과·한계·학습 준비 방향은 [검증 기록](rag-test-report-2026-10-07.md)을 참고한다.

## 실제 평가에서 반영한 보완

- 일반적인 절차·조건 질문에는 조건부 안내를 제공하고, 개별 판정에 부족한 사실만 별도로 확인하게 했다.
- 중앙부처 해석 문서에서 질문·질의요지를 회답과 분리했다. 제목의 물음을 긍정 사실로 사용하는 오류를 평가 항목에 추가했다.
- 층간소음 문단에는 공동주택/비공동주택 적용 범위를 저장한다. 아파트·연립·다세대와 다가구·오피스텔이 명시된 질의는 반대 범위의 문단을 제외한다. 복합하거나 불명확한 경우에는 둘 다 검색하고 사실 확인을 요청한다.
- 물음표로 구분된 질문이 2~3개인 민원은 질문별로 검색·재정렬하고 각 질문의 상위 근거를 우선 확보한다. 전체 민원을 그대로 답변 생성에 전달한다.
- 초기 후보 수는 질문당 6개, 생성 근거는 최대 4개다. 마지막 토큰 로짓만 계산하며 질의 임베딩 후 임베딩 모델을 해제해 GPU 메모리 경합을 줄인다.
- 공식 HTML과 추출 파일은 해시가 포함된 파일명으로 저장해 새 수집이 이전 원문 파일을 덮어쓰지 않게 했다.
- 출처 ID 외에 답변 속 `[번호]`도 검사한다. 번호 검사는 문장 전체의 의미가 원문에서 뒷받침되는지를 보장하지 않는다.

실제 HTTP 경로에서 신규 입력 7건과 기존 민원 선택 2건을 시험하는 명령:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_rag_api.py --output ../docs/ai-expected-answer/rag-live-api-evaluation-2026-10-07.json
```

이 스크립트는 본인이 만든 임시 테스트 계정·민원만 사용하고 완료 후 해당 테스트 데이터만 정리한다. 실모델, 로그인, 추천 요청, 진행 상태 조회, 생성 결과 저장을 함께 검증한다.

채팅의 두 차례 질문을 실제 모델과 HTTP 경로로 확인하는 명령:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_rag_chat.py --output ../docs/ai-expected-answer/rag-chat-evaluation-2026-10-07.json
```

DB를 공유하는 서버 회귀 테스트와 실제 모델 시험은 차례로 실행한다. 서버 시작 복구 처리를 시험하는 회귀 테스트가 대기·진행 중 추천 작업을 실패로 표시할 수 있기 때문이다.
