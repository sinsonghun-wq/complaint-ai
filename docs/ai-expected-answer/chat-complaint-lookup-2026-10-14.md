# 챗봇의 민원 조회·검색

최초 구현·검증일: 2026-10-14. 선택 조건 완화: 2026-10-19.

## 사용 방법

`AI 추천 답변`에서 `조회하고 싶어`라고 말하거나 옵션의 **특정 민원 조회**를 선택한다. 챗봇이 **어떤 민원들을 조회하시겠습니까?**라고 묻고 조건 카드를 보여준다.

- 현재 7개 부서: 노동·기업 / 교통·국토 / 주택·건축 / 환경·위생 / 문화·행정·안전 / 보건·복지 / 기타.
- 부서는 복수 선택할 수 있다. 선택한 부서 중 하나에 해당하면 조회한다.
- 상태는 **미접수 / 접수 중 / 접수 완료** 중 하나를 선택하거나 **전체 상태**로 둘 수 있다.
- **부서 또는 상태 중 하나만 선택해도 조회하기를 누를 수 있다.** 부서만 선택하면 해당 부서의 모든 활성 상태, 상태만 선택하면 모든 부서의 해당 상태를 조회한다.
- 둘 다 선택하면 선택한 부서 내에서 해당 상태로 좁힌다(미접수의 기존 부서 무관 정책은 아래 설명대로 유지). 아무것도 선택하지 않으면 조회 버튼은 비활성화된다. 오른쪽 도구에는 본인 민원만 표시한다.
- 대화창 조건 카드, 오른쪽 민원 도구 조회 옵션, 작성한 민원 화면의 공통 필터와 실제 목록/건수 API에 동일하게 적용된다. 모델 호출이나 DB 구조 변경은 필요하지 않다.

**미접수**는 담당 부서가 없는 민원이다. 사용자 확인에 따라 선택한 부서와 관계없이 본인의 부서 미정 민원을 모두 조회한다. **접수 중**은 담당 부서가 정해졌지만 공식 답변이 전송되지 않은 민원이며 관리자 임시 답변도 여기에 포함된다. **접수 완료**는 공식 답변이 전송된 민원이다. 업무 상태만 완료로 표시되고 전달된 답변이 없는 비정상 자료는 접수 중으로 조회한다. 취소·삭제 건은 조건 조회와 검색에서 제외한다.

오른쪽 도구의 **조회 옵션**과 왼쪽 **작성한 민원** 화면의 **특정 민원 조회**에서도 같은 조건을 수동으로 선택한다. **조건 초기화**로 전체 목록을 확인한다. 민원인 목록의 상태 표시는 위 세 상태를 사용한다. 기존 수정·삭제 권한은 실제 업무 상태에 따른다.

`검색하고 싶어`라고 말하거나 옵션의 **민원 검색**을 선택하면 **어떤 민원을 검색하시겠습니까?**라는 안내가 나온다. 찾고 싶은 상황이나 내용을 다음 메시지에 1,000자 이내로 적는다. 제목이 정확하지 않아도 된다. **안내 직후의 메시지 한 번만 검색어로 소비**하며 이후 메시지는 일반 상담으로 돌아간다. **검색 취소**, 새 대화, 다른 도구·조회 옵션 선택으로 검색 준비를 종료할 수 있다.

검색을 시작하면 오른쪽 도구를 바로 열고 찾는 중임을 표시한다. 완료 후 위에는 **검색된 민원**, 아래에는 **검색과 유사한 민원**을 보여준다. 각 목록은 10건씩 별도로 넘길 수 있다. 민원을 선택하면 기존 상세 확인·공식 답변·수정·삭제 확인·재민원·AI 추천 답변 기능을 그대로 이용한다. 상세에서 목록으로 돌아가도 조회 조건과 검색 결과를 유지한다.

검색 오류는 재시도할 수 있으며 재시도는 동일한 검색어를 사용한다. 실패하더라도 다음 채팅을 다시 검색어로 소비하지 않는다. 결과가 없으면 빈 결과를 표시한다. 수정·삭제를 자동으로 실행하지 않는다.

## 구성

`POST /api/ai-recommendations/intent`는 로컬 `qwen3.5:4b`로 `filter / search`를 포함한 요청을 구분한다. `filter`는 조건 카드를, `search`는 다음 메시지의 검색 준비만 실행한다. 기존 응답 구조와 실제 민원 작업 API를 유지한다.

`GET /api/complaints?departments=...&departments=...&view_status=in_progress`는 본인 범위에서 DB 필터·건수·페이지를 함께 적용한다. 실제 부서 명칭, 필수 선택, 단일 상태를 서버에서도 검사한다.

`POST /api/ai-recommendations/complaint-search`는 `{ "query": "..." }`를 받아 본인의 활성 민원 전체를 읽고, 제목과 내용의 모든 구간을 문맥 크기 안의 배치로 나눠 Qwen3.5-4B로 검색한다. 한 배치에는 최대 4개 구간을 담는다. `direct / similar / irrelevant`의 엄격한 JSON 결과를 받아 일치와 유사 결과를 나눠 반환한다. 각 배치의 고유 민원 수로 결과 개수를 고정하고 해당 배치의 번호만 출력할 수 있도록 제약한다. 생성량도 최대 256토큰으로 제한한다. 같은 핵심 문제·피해 현상·해결 조치의 실질적인 공통점이 있어야 유사 결과로 판단하며, 시간·장소·부서만 공통인 것은 제외하도록 지시한다. 특정 주제의 단어를 하드코딩하지 않는다.

검색은 기존 민원 임베딩이나 공식 자료 RAG 색인을 이용하지 않는다. 기존 1,536차원 민원 벡터와 1,024차원 RAG 벡터를 혼용하지 않으며 별도 DB 이전도 필요 없다. Qwen3.5-4B가 유사 후보로 고른 민원은 **Qwen3-Reranker-0.6B**가 본인 민원용 고정 지시문으로 한 번 더 검토한다. 원문의 모든 구간을 검사해 민원별 최대 관련성 점수가 `COMPLAINT_SEARCH_MIN_RELEVANCE`(기본 0.35) 이상인 후보만 유사 결과에 포함하고 점수 순으로 표시한다. 이 점수는 확률이나 검증된 정확도 지표가 아니다.

재정렬 서비스는 `strict_context=true`에서 검색어를 보존하고 문서를 토큰 구간으로 나눠 끝부분까지 검사한다. 구간 경계는 일부 겹치게 해 경계의 내용을 보존한다. 검색어 자체가 문맥 범위를 넘으면 명시적으로 거부한다. 검색 클라이언트는 `context_policy=complete_document` 응답을 요구해 구버전의 조용한 잘림을 방지한다. 모델 장애는 유사 검토 오류로 표시한다. 기존 공식 RAG 요청은 기본 공식 자료 지시문과 기존 처리 경로를 유지한다. 개인 민원은 설정된 로컬 Ollama 및 로컬 재정렬 서비스에서 처리한다.

소유자 ID는 로그인 정보에서 가져온다. 타인·삭제·취소 민원과 관리자 임시 답변을 제외하고, 모델이 만든 번호·누락·중복·잘못된 JSON을 검사한다. 추론 후 소유권·활성 상태·원문 및 상태 변경을 다시 확인한다. 수정된 원문은 이전 검색 분류에 남기지 않고 제외하며 재검색을 안내한다. 화면의 상태 갱신은 현재 두 결과 페이지의 최대 20개 ID만 대상으로 한다.

모델 장애는 검색 오류로 표시하며 키워드 검색을 LLM 결과라고 표시하지 않는다. 민원이 많거나 원문이 길면 배치가 늘어 검색 시간이 길어진다. 대규모 사용에는 본인 민원용 별도 임베딩 색인으로 후보를 좁힌 뒤 LLM으로 판단하는 확장이 적합하다. 현재 구현은 전체 본인 원문을 검사하므로 첫 페이지 이후의 민원을 누락하지 않는다.

## 최초 구현 당시 검증 (2026-10-14)

- 최종 서버 전체 회귀 시험 **145건 통과**. 실제 PostgreSQL 조회 필터·소유권·페이지·임시 답변 비공개와 검색 모델 장애·잘못된 번호·긴 원문·전체 대상 배치·유사 후보 검증을 포함한다. 재정렬 서비스 별도 시험 **3건 통과**: 원문 끝부분의 관련성 보존과 구간 점수 합산, 과도한 검색어 명시적 거부, 기존 공식 RAG 지시문·처리 경로 유지.
- 화면 테스트 **71건 통과**: 챗봇 19, 도구 통합 15, 도구 창 24, 기존 업무 화면 9, 가져오기 진행률 4. 부서·상태 필수 선택, 검색 메시지 한 번 소비, 상담 복귀, 한글 조합 입력, 로딩·중복 방지·재시도·빈 결과·취소, 검색 결과 수정·삭제·페이지·외부 원문 변경을 확인했다.
- React 최종 빌드 통과.
- 실제 Qwen 요청 구분은 초기 **14/17**, 프롬프트 보완 후 최종 **17/17** 통과. 번호를 지정한 확인, 검색 방법 설명, 선택 민원 수정의 번호 전달을 보완했다. [초기와 최종 기록](chat-lookup-intents-2026-10-14.json)을 보존했다.
- 실제 검색은 합성 민원으로 표현이 다른 요청·혼동·무관한 요청·소유권·임시 답변 비공개·동일 상세 API를 시험한다. [초기 검색 기록](complaint-search-evaluation-2026-10-14.json), [중간 모델 응답 오류](complaint-search-evaluation-v2-model-error-2026-10-14.json), [재정렬 추가 전 기록](complaint-search-evaluation-v3-before-reranker-2026-10-14.json)을 보존했다. [재정렬 실측](complaint-search-reranker-probe-2026-10-14.json)에서 관련·불필요 후보 점수의 차이를 확인하고 유사 후보 검증을 추가했다. [최종 검색 기록](complaint-search-evaluation-final-v4-2026-10-14.json)에 보완 후 결과를 저장한다.

최종 실제 검색 **6건 모두 통과**, 동일 상세 API·타인 접근 차단과 임시 자료 정리 **2개 단계도 통과**했다. 초기 강화 검토의 정밀성 3/6, 재정렬 추가 전 4/6에서 최종 6/6으로 개선됐다. 최종 시험은 7개의 합성 활성 민원과 타인·취소·삭제 차단용 자료를 사용했다. 소음, 도로 파손, 임금, 예방접종, 신호등 가림, 관련 없는 요청을 포함하며 예시를 운영 규칙으로 하드코딩하지 않았다. 일치하는 민원 검색, 불필요한 유사 후보 제외, 임시 답변 비공개를 확인했다.

현재 기기의 실제 검색 시간은 약 **27~49초**였다. 첫 모델 적재가 포함된 첫 시험이 48.69초, 이후 시험이 27.16~29.60초였다. 본인 민원 수와 원문 길이가 늘면 시간이 증가한다. 정확도 지표는 이 소규모 합성 시험의 결과이며 일반 운영 정확도로 해석하지 않는다.

실제 검색 시험은 새로 만든 임시 계정과 합성 민원만 사용하고 정확히 그 자료만 정리한다. 기존 민원을 검색 평가 자료로 반출하지 않는다. 화면 검증은 React DOM 시험이며 실제 브라우저의 시각 검증은 수행하지 않았다. 소규모 모델 시험은 모든 민원의 검색 정확도를 보장하지 않는다. 모델 가중치 추가 학습은 수행하지 않았다.

최종 코드로 웹 서버·개발 화면·재정렬 서비스를 실행하고 로컬 상태 응답을 확인했다. 기존 화면 주소 `http://127.0.0.1:5173/`에서 사용할 수 있다.

## 선택 조건 완화 검증 (2026-10-19)

- 조회·소유권·건수·페이지·잘못된 조건 검증 8개와 기존 관리자 부서 권한 회귀 11개, 총 백엔드 19개 통과.
- 공통 필터·AI 추천 답변 카드·오른쪽 도구의 단독 조건 연결 8개를 추가했고, 기존 화면 및 권한 회귀를 포함한 React 테스트 49개 통과. React 빌드 성공.
- 실행 중인 main 전용 API(5174 프록시 → 8000)에서도 임시 계정으로 부서 단독, 접수 완료 단독, 접수 중 단독, 미접수 단독, 부서+상태 조합의 결과와 total을 확인했다.
- 타인 민원·취소·삭제 건은 제외하고 관리자 임시 답변은 공개하지 않는 것을 확인했다. 생성한 임시 계정·민원·답변만 정리했으며 기존 데이터는 보존했다.
