# 임베딩 한도와 RAG 행별 예외 처리

`final.csv` 19행은 CSV 파싱 이후 임베딩 요청에서 실패했다. Ollama 0.40.6의
기본 물리 배치가 2,048토큰인데 해당 본문은 2,154토큰이었다.
기존 임베딩 함수는 HTTP 오류를 `None`으로 바꿔 차원 오류로 잘못 표시했고,
RAG 가져오기는 한 행의 오류로 전체 작업을 종료했다.

## 적용한 한도

모델 `bge-m3:latest`와 1,024차원, DB 접속 설정, 추천 답변 검색·프롬프트는 유지한다.
공통 임베딩 요청의 `num_ctx`와 `num_batch`를 모두 4,096으로 지정한다.
서로 다른 요청 옵션으로 같은 모델이 반복 로드되는 일을 피하려고 저장·검색 요청에
같은 옵션을 사용한다. LLM의 32,768 컨텍스트 설정과는 별개다.
환경 변수 `EMBEDDING_NUM_CTX`, `EMBEDDING_NUM_BATCH`로 조절할 수 있고 최대는 8,192다.
이는 [BGE-M3의 공식 최대 길이](https://huggingface.co/BAAI/bge-m3)다.

GTX 1060 3GB에서 동일한 573토큰 입력을 설정별 1회 준비 후 3회 측정했다.
초기 모델 로드 시간은 반복 속도에서 제외했다.

| 물리 배치 / 컨텍스트 | 짧은 입력 중앙값 | 전체 GPU 사용량 | 19행 2,154토큰 | 긴 입력 6,597토큰 |
|---|---:|---:|---|---|
| 2,048 / 4,096 | 0.2428초 | 1,687MiB | HTTP 413 | 미측정 |
| 4,096 / 4,096 | 0.2431초 | 1,789MiB | 0.9830초, 정상 | 길이 초과로 제외 |
| 8,192 / 8,192 | 0.2442초 | 2,060MiB | 0.9879초, 정상 | 5.3266초, 정상 |

8,192에서 짧은 입력 차이는 약 0.6%로 이 측정에서는 작았고, 메모리는 약 350MiB 늘었다.
모든 부하에서 성능 영향이 0이라는 뜻은 아니다. 긴 입력은 실제 연산량이 늘고,
다른 프로그램이 GPU 메모리를 많이 쓰는 경우에도 처리 시간이 달라질 수 있다.

이후 8080번 답변 모델도 함께 실행하자 전체 GPU 사용량이 약 2,719MiB로 늘었다.
따라서 실제 기본값은 기존 대비 약 100MiB만 늘어나는 4,096으로 선택했다.
8,192는 모델의 기술적 상한이며, 3GB GPU에서 두 모델을 함께 켜는 현재 운용의
기본값으로 권장하지 않는다. 위 표는 답변 모델을 켜기 전의 측정이다.

## 예외 처리

- RAG 가져오기는 `truncate=false`를 사용한다. 한도 초과 본문을 조용히 자르지 않는다.
- 입력 길이·임베딩 요청/응답·벡터 검증 오류는 해당 행만 `rag_import_failures`에 기록한다.
- 실패한 요청 때문에 다음 행의 임베딩을 30초 동안 생략하지 않는다.
- 잘못된 DB 값도 행별 세이브포인트로 격리한다. 연결 장애 등 작업 자체의 오류는 별개다.
- 유효한 본문과 벡터만 `department_documents`에 넣는다.
- 100개 원본 레코드마다 저장·중복·예외 건수와 체크포인트를 함께 확정한다.
- 완료 결과에 `처리하지 못한 항목 N건 제외`를 표시한다. N이 0이면 안내와 목록을 숨긴다.
- 별도 목록을 펼치면 헤더를 포함한 CSV 행 번호와 사유를 20건씩 볼 수 있다.
  API는 본인 작업에만 접근을 허용한다.
- 실패한 과거 작업의 기록은 유지하며, 임의로 실제 파일을 재실행하지 않는다.

## 검증

격리된 PostgreSQL DB에서 19행 및 뒤쪽 행의 임베딩 실패를 주입해도
205건 끝까지 처리하고 203건 저장·2건 제외되는 것을 확인했다.
실제 저장과 카운터는 100 → 200 → 205건으로 함께 확정됐다.
벡터 없음/잘못된 차원/0 벡터, DB 행 오류, 다음 정상 행 저장, 취소,
예외 목록 권한·페이지 처리와 예외 0건 숨김을 검사했다.

실제 모델과 격리된 DB·브라우저에서는 원본 파일의 첫 20건에 빈 본문과 정상 자료를
추가한 22건을 8,192 설정으로 처리했다. 19건 저장·3건 제외로 완료했고,
기존 오류가 났던 CSV 19행과 마지막 정상 행도 저장됐다. 테스트 DB는 제거했다.
백엔드 테스트 20개, 관리자 UI 79개와 진행률 4개, 프런트엔드 빌드가 통과했다.

## 실행 상태 확인

Ollama(11434)는 임베딩, 별도 llama-server(8080)는 분석·답변 생성용이다.
`LLM_BACKEND=llama_server`이므로 Ollama만 켜도 8080 연결 경고는 해결되지 않는다.
2026-10-21 확인 당시 8080 프로세스가 없었고, 기존 예약 작업은 수동 실행용이며
자동 시작 트리거가 없었다. 기존 모델·어댑터·32,768 컨텍스트 설정으로 작업을 다시
실행해 `/health`의 HTTP 200을 확인했다. 11434와 8000의 상태 확인도 모두 200이다.

백엔드와 RAG 워커에 4,096 설정을 반영했다. 실제 Ollama 실행 명령에서도
`-c 4096 -b 4096 -ub 4096`을 확인했다. 두 모델 실행 상태의 GPU 사용량은 약 2,794MiB다.
사용자가 다시 업로드한 작업은 이전 워커 종료 시 저장된 체크포인트를 유지한 채
같은 작업 ID로 새 워커가 이어받았고, 총 45,526건을 확인한 후 처리 중이다.
