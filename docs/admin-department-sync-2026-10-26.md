# 관리자 부서 연결 및 이름 동기화

## 적용 결과

현재 서비스 DB `complaintai`의 실제 부서 ID를 사용했다. 부서 번호를 정적 JSON
목록에 맞춰 다시 매기지 않았다.

| 로그인 ID | 관리자 표시 이름 | department_id | 답변 작성 부서 |
| --- | --- | --- | --- |
| admin-administration-safety | 문화·행정·안전 관리자 | 1 | 문화·행정·안전 |
| admin-land-transport | 교통·국토 관리자 | 2 | 교통·국토 |
| admin-housing | 주택·건축 관리자 | 3 | 주택·건축 |
| admin-environment | 환경·위생 관리자 | 4 | 환경·위생 |
| admin-welfare | 보건·복지 관리자 | 5 | 보건·복지 |
| admin-fire | 노동·기업 관리자 | 6 | 노동·기업 |
| admin-other | 기타 관리자 | 7 | 기타 |

계정의 UUID, 소유자 ID, 로그인 ID, 비밀번호 salt와 hash는 보존했다.
민원 1건, 답변 0건, RAG 원문 99,235건, 조각 160,014건도 적용 전후 동일하다.
적용 전 계정 표시 이름과 부서 연결은 Git에서 제외되는 `logs/`에 별도 저장했다.

## 재발 방지

`database/migrations/20261026_admin_department_sync.sql`은 반복 실행할 수 있는
추가 마이그레이션이며, 백엔드 시작 시 `ensure_admin_department_identity()`로 적용한다.

- 기존에 부서가 NULL인 초기 관리자 계정만 실제 DB의 해당 부서 이름으로 찾아 연결한다.
  이미 연결된 계정은 로그인 ID에 과거 부서명이 남아 있어도 그 숫자 ID를 유지한다.
- `departments.name`을 SQL이나 pgAdmin에서 변경하면 DB 트리거가 동일한 ID에 연결된
  모든 관리자의 `display_name`을 `현재 부서명 + ' 관리자'`로 갱신한다.
- 관리자 생성, 부서 재지정, 표시 이름 변경 시에도 DB의 실제 부서명으로 이름을 맞춘다.
- CHECK 제약으로 부서 ID가 없는 관리자 생성과 부서 연결 해제를 거부한다.
  존재하지 않는 부서 ID는 외래 키와 트리거가 거부한다.
- 과거 자료를 복원했을 때 알 수 없는 계정의 NULL 부서를 임의 추정하지 않는다.
  이런 기존 계정은 권한을 부여하지 않으며, 새 NULL 관리자 입력은 계속 차단한다.
- 인증 API는 DB에서 조인한 현재 부서명으로 관리자 표시 이름을 반환한다.
  민원 조회 API의 `department_name`도 현재 부서 테이블을 기준으로 제공한다.
  과거 `complaints.category` 문자열이나 원문은 변경하지 않는다.
- 화면은 계정 정보와 부서 목록을 5초마다 다시 확인하고, 창으로 돌아올 때 즉시 확인한다.
  같은 로그인 토큰에서도 새 이름과 재지정된 부서 권한이 반영된다.
  표시 이름 갱신으로 진행 중인 채팅 요청의 API 함수가 교체되지 않도록 토큰 기준으로 유지한다.

따라서 같은 부서 ID의 이름이 바뀌면 관리자 이름과 표시 부서가 함께 바뀌고,
민원 접수·답변 권한은 기존 숫자 ID 연결을 유지한다. 로그인 ID는 자동 변경하지 않는다.

## 검증

- 별도 임시 DB에서 NULL 계정 복구, 자격 정보 보존, 직접 SQL 부서명 변경,
  기존 토큰의 권한 유지, 부서 재지정, 다른 부서 변경 차단, NULL/없는 부서 거부,
  반복 마이그레이션을 검사했다.
- 화면에서 주기적 이름 갱신과 같은 토큰의 부서 재지정을 검사했다.
- 실제 실행 중인 서버에서 관리자 7명의 계정 정보와 부서 컨텍스트가 모두 HTTP 200이고,
  기존 교통·국토 민원은 교통·국토 계정만 `can_manage=true`인 것을 확인했다.
- 프런트 관리자 회귀 테스트 86개, 진행률 테스트 4개와 프로덕션 빌드를 통과했다.
- 백엔드 전체 테스트 146개를 통과했다. 실제 서비스 DB를 초기화하지 않고 별도 임시 DB에서 실행했다.
