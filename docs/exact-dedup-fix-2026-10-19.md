# 파일 원문 중복 저장 보완 (2026-10-19)

적용 대상은 별도 `complaint AI-main` 폴더의 5174 화면과 8000 FastAPI, 5440 PostgreSQL이다. GitHub로 push하거나 원래 complaintAI 폴더를 변경하지 않았다. 모델·임베딩·RAG 설정도 변경하지 않았다.

## 변경한 기준

- 중복 판정 대상은 기존처럼 **민원 본문**이다. 제목/파일명/확장자/부서명은 포함하지 않는다. 반복 공백·줄바꿈은 기본적으로 한 칸으로 정리한다. 표현이 비슷하다는 이유로 제외하지 않는다.
- `raw_content_fingerprint`는 **개인정보 마스킹 전** 본문을 정리한 SHA-256이다. 기존 `content_fingerprint`는 호환성을 위해 남기지만 파일 중복 판정에는 사용하지 않는다.
- `dedup_compact_fingerprint`는 공백을 제외한 글자열의 지문으로, 비교 후보를 좁히는 용도일 뿐이다. 이 값 하나로 중복 처리하지 않는다.
- `dedup_profile`에 원문 지문, 공백 위치와 PDF의 물리적 줄바꿈 위치를 보관한다. 원문 문자열·전화번호·이메일은 이 프로필에 넣지 않는다.

## PDF 공백 보정 범위

PDF에서 `퇴직급여`가 `퇴\n직급여`로 잘리면 기존 방식은 `퇴 직급여`라는 새 본문으로 취급했다. 이제 네이티브 텍스트 추출의 줄바꿈 위치를 별도로 기록한다.

중복 판정 조건은 다음을 모두 충족해야 한다.

1. 공백을 제외한 글자·숫자·문장부호의 전체 순서가 정확히 같다.
2. 공백 위치의 차이는 기록된 PDF 줄바꿈 경계에만 존재한다.

따라서 `아버지가 방에`와 `아버지 가방에`처럼 원래 존재하는 띄어쓰기가 다르면 별도 민원이다. 문장부호/전화번호/단어가 달라도 별도 저장한다. 공백 전체 제거, 임베딩 유사도 임계값, LLM의 의미 판단으로 중복을 제외하지 않는다.

이 보정은 **중복 비교 시의 형식 차이 보정**이다. 참조 원문 없이 PDF의 모든 띄어쓰기를 추측해 다시 쓰는 기능이 아니다. PDF만 먼저 넣었을 때 표시 본문에 줄바꿈 공백이 남을 수 있지만, 나중에 같은 XLSX/HWP를 넣어도 중복으로 제외한다. PDF 원본 자체가 줄 끝의 공백을 잃은 경우 원래의 단어 경계는 완벽히 복원할 수 없다. 네이티브 사례 본문의 단일 줄바꿈 경계에만 제한하고, 문단 구분/명시된 띄어쓰기/일반 입력/OCR 추정 공백에는 확대 적용하지 않는다. OCR 오인식으로 실제 글자가 달라진 것은 자동으로 합치지 않는다.

## 마스킹 전 지문 전달 및 저장

- XLSX/HWP/PDF/이미지/기존 CSV intake가 마스킹 전에 지문을 계산한다. 미리보기 본문은 마스킹을 유지한다.
- `/api/intake` → React → `/api/complaints/batch` 사이에는 원문 자체가 아닌 서버 HMAC 서명 `dedup_token`을 전달한다. 내용 또는 토큰이 변조되면 HTTP 422와 재업로드 안내를 반환한다. 서명은 기존 `AUTH_TOKEN_SECRET`을 사용하며 운영에서는 반드시 강한 비밀값을 설정한다.
- CSV 전용 워커도 원본 행에서 분석·마스킹 전에 지문을 계산해 저장까지 유지한다. 요약문 또는 마스킹된 본문으로 원문 지문을 덮어쓰지 않는다.
- 일반 민원인의 접수·수정에도 원문 지문을 기록한다. 수정한 내용이 같은 소유자의 다른 활성 민원과 겹치면 HTTP 409로 안내한다. 기존 상태 제한은 유지한다.

## DB 제약 및 동시 요청

`complaints_active_raw_unique`는 `(owner_user_id, raw_content_fingerprint)`의 활성 민원 부분 고유 인덱스다. PostgreSQL 16의 `NULLS NOT DISTINCT`로 관리자 공용 소유자 NULL도 하나의 범위로 취급한다. 취소/삭제 보관함은 인덱스와 중복 조회에서 제외한다. 서로 다른 일반 사용자는 여전히 다른 소유자 범위다. 관련 PostgreSQL 문서는 [고유 제약](https://www.postgresql.org/docs/16/ddl-constraints.html)을 참고한다.

글자열이 같지만 PDF 줄바꿈 형태가 다른 경우도 한 번만 저장되도록 소유자+글자열 후보 지문 단위 트랜잭션 잠금을 사용한다. 500건 묶음의 키는 정렬해서 취득하므로 순서가 반대인 동시 묶음도 교착되지 않는다. 최종 INSERT에는 `ON CONFLICT DO NOTHING`을 사용한다. 모든 공백 제거 지문에 고유 제약을 걸지는 않는다.

삭제 보관함에서 관리자 전용 복원 시에도 같은 원문의 활성 관리자 민원이 있으면 409로 복원을 거부하고 보관함에 그대로 둔다. 기존 취소·완료 상태 관리와 민원인에게 돌아가지 않는 복원 정책은 유지한다.

## 기존 DB 이전

- 추가형 SQL: `database/migrations/20261019_exact_dedup.sql`.
- 신규 DB용 `database/init.sql`에도 3개 컬럼/후보 인덱스/부분 고유 인덱스를 추가했다. **기존 데이터에 init.sql을 실행하지 않는다.**
- FastAPI 시작 및 CSV 워커 시작 시 `app.dedup.ensure_dedup_schema()`가 추가형 SQL과 기존 데이터 지문 보충을 수행한다. 이전 중에는 쓰기를 잠깐 막고 단일 트랜잭션으로 적용한다. 추가 환경 변수는 없다.
- 기존 원문이 마스킹되어 `[개인정보 제외]`만 남았다면 원문 지문을 복구할 수 없으므로 `legacy_original_unavailable`로 표시하고 지문을 만들지 않는다. 이런 과거 데이터는 원본 파일 재확인 없이는 완전한 중복 확인이 불가능하며 재업로드 때 한 번 더 저장될 수 있다.
- 과거에 이미 저장된 동일 본문을 자동 삭제하지 않는다. 같은 소유자·동일 활성 본문이 있으면 대표 행만 고유 키를 가지며 나머지는 `legacy_duplicate_of`를 기록해 원본/답변을 보존한다. 과거 PDF 줄바꿈 위치는 사라졌을 수 있어 임의로 추정하지 않는다.
- 실제 로컬 DB는 민원 144건/계정 9개/답변 1건을 유지했다. 이전 전후에 새 지문 컬럼을 제외한 모든 기존 민원 필드·계정·답변의 체크섬이 각각 같았다. 기존 중복 건을 정리하거나 민원을 추가하지 않았다.
- 이전 전 개발 DB 백업은 Git에서 제외되는 `tmp/main-runtime/complaintai-before-exact-dedup-20261019.dump`에 보관했다. 개인정보·계정 해시가 포함될 수 있으므로 외부 공유/커밋하지 않는다.

## 검증

원본 72건의 XLSX/HWP/PDF를 실제 `/api/intake`로 추출하고 `/api/complaints/batch`로 별도 임시 DB에 저장했다. LLM/임베딩만 대체했으며 추출/서명/중복 SQL/고유 제약은 실제 코드로 수행했다. 테스트 DB와 업로드 임시 파일은 정리한다.

`tests/test_exact_dedup.py` 17개에는 전화번호/이메일 차이, 실제 띄어쓰기 차이, 의미만 비슷한 문장, 토큰 변조, CSV↔문서 중복, 동시 동일/PDF 업로드, 반대 순서 묶음, 고유 제약 직접 SQL 우회 차단, 민원인 수정 및 기존 데이터 보존도 포함한다. 기존 CSV 파이프라인·부서 권한·삭제 보관함·파일 추출·워커·조회 필터의 관련 회귀도 실행한다. 전체 프로젝트 테스트가 아니라 이 변경과 관련된 범위의 검증이다.
