# 긴 RAG 원문 처리

## 유지되는 동작

- 기존 BGE-M3 임베딩 모델, 1,024차원 벡터, Ollama 설정을 사용한다. 실제 `.env`를 바꾸지 않는다.
- 8,192토큰 이하 본문은 기존처럼 `department_documents.content`와 `embedding`에 저장한다. 기존 100행 단위 확정 저장과 완전 일치 본문 중복 검사를 유지한다.
- 긴 원문이 없는 DB에서는 기존 검색 SQL(상위 3건, 각 본문 앞 5,000자)을 그대로 사용한다.
- 채팅 API, 프롬프트, 답변 생성 모델과 응답 형식을 유지한다. `aiFAQ`의 자료 검색 함수만 확장한다.
- 기존에 저장된 자료를 자동으로 재임베딩하거나 다른 테이블로 이동하지 않는다.

## 가져오기 순서와 저장 위치

1. CSV를 읽으며 BGE-M3 공식 고정 버전 토크나이저로 길이를 확인한다. 긴 원문 전체를 임베딩 서버에 보내지 않는다.
2. 8,192토큰을 초과하면 원문 전체를 `department_documents`의 한 행에 먼저 보존하고 후순위로 표시한다. 이 행의 직접 임베딩은 만들지 않는다.
3. 파일의 짧은 원문을 모두 처리한 다음 긴 원문을 조문·문단 경계에 따라 나눈다. 연속 문자 구간으로 저장하므로 공백을 포함한 원문을 정확히 복원할 수 있다.
4. 조각은 **`department_documents_chunks`**에 저장한다. `parent_id`가 원문 ID이며 `chunk_index`, 문자 시작·끝 위치, 조각 본문, 토큰 수, 벡터가 들어간다. 조각마다 DB가 생기는 구조가 아니다.
5. **`department_documents_chunk_state`**는 원문별 상태, 조각 완료 수, 전체 본문 해시, 임베딩 모델, 분할 방식, 조문 연결 정보와 제공된 법령 정보를 관리한다.
6. 긴 원문의 각 조각을 완료할 때마다 해당 조각을 확정 저장한다. 새 짧은 자료 작업이 대기하면 다음 조각 전에 양보한다. 이미 진행 중인 임베딩 요청을 강제 선점하지는 않는다.
7. 모든 조각의 임베딩과 원문 전체 구간 일치를 확인한 뒤 `ready`로 게시한다. 대기·처리·취소·실패 상태의 긴 원문은 검색 대상에서 제외한다.

조각의 목표 상한은 여유를 둔 7,500토큰이고 실제 상한은 8,192토큰이다. 작은 조항은 한 조항씩 보존하므로 조각 수가 단순한 `전체 토큰 수 / 8,192`보다 많을 수 있다. 법령 구조가 없는 자료는 작은 문단 구간을 사용한다.

## 취소·실패·재개

- 취소하면 원문과 확정 저장된 조각을 보존한다. 미완성 원문은 검색에서 숨긴다.
- 한 긴 원문의 조각 생성이 실패해도 다음 원문 처리를 계속한다. CSV 행 번호와 사유를 기존 제외 항목 영역에 표시한다. 제외 건수가 0이면 문구를 표시하지 않는다.
- 작업 종료 후 **긴 원문 이어서 처리** 버튼을 누르면 같은 작업에서 미완성 원문만 재개한다. 이미 만들어진 벡터는 다시 만들지 않는다.
- 짧은 원문을 모두 읽은 작업은 저장된 원문으로 재개하므로 CSV를 다시 업로드하지 않아도 된다. 짧은 원문 읽기 도중 취소했다면 기존 CSV 체크포인트도 이어서 사용한다.
- 서버·워커 중단은 기존 워커 감지 기능으로 실패 상태가 된다. 이어서 처리할 원문이 있으면 같은 재개 버튼을 사용한다. 과거 취소 작업을 배포 시 자동 재시작하지 않는다.
- 원문 해시, 임베딩 모델 또는 분할 방식이 달라졌다면 기존 조각을 임의로 섞지 않고 사유를 알린다.

## 검색과 근거 연결

- 짧은 자료 벡터와 완료된 긴 자료의 조각 벡터를 같은 거리 기준으로 비교하고 상위 3개 원문을 선택한다. 한 원문의 조각이 결과 전체를 독점하지 않도록 원문 ID별로 묶는다.
- 적중 조각의 조문 전체, 인접 예외, 선택 조문을 역으로 참조하는 예외, 정의·적용 범위를 함께 확인한다.
- `제3조`, `별표 2` 등 원문 내부 참조를 따라간다. 줄바꿈 없는 조문과 순환 참조도 처리한다.
- 명시적으로 이름이 제공된 다른 법령은 자료명과 조항을 확인해 추가 조회한다. 참조 대상은 완료된 긴 자료 또는 기존 짧은 자료일 수 있다. 각 근거는 원문 ID·자료명으로 구분한다.
- 긴 원문 CSV의 선택 열: `법령ID`/`law_id`, `개정정보`/`law_version`, `시행일`/`effective_date`. 시행일은 `YYYY-MM-DD`를 권장한다. 기존 `department_documents.version`의 CSV 행 번호를 법령 개정본으로 해석하지 않는다.
- 같은 법령의 개정본은 제공된 시행일로 구분한다. 질문에 날짜가 있으면 해당 시점을, 없으면 현재 날짜를 기준으로 한다. 버전이 모호하면 임의로 고르지 않는다.
- 참조 조문이 없거나 중복되어 대상을 확정할 수 없으면 일부 규정만 전달하지 않고 근거 미확인 사실을 전달한다. 제공되지 않은 시행일이나 개정 정보를 추정해서 만들지 않는다.
- 연결 근거가 답변의 문맥 한도를 넘으면 일부 예외를 잘라내지 않고 근거 한도 초과를 알린다. 기존 짧은 자료의 본문 길이 정책은 유지한다. 2026-10-23부터 긴 원문 근거는 질문당 합계 최대 5,000자로 제한하며, 조항 추가 전에 분량을 검사해 초과 참조 확장을 중단한다. 현재 시간 제한 등은 [근거 분량 설정](rag-evidence-budget-2026-10-23.md)을 참고한다.

이 처리는 법령 구조와 참조 정보를 이용한 안전장치다. 원본에 잘못된 내용이 있거나 조문 표기·법령명이 불명확한 경우까지 법률적 정확성을 보장하지는 않는다. 이 경우 검색에 실패하거나 근거 미확인으로 처리할 수 있다.

## 설치와 DB 변경

- 추가 의존성: `tokenizers==0.22.2` (`dcm-back/requirements.txt`).
- 공식 BGE-M3 토크나이저를 `dcm-back/data/tokenizers/bge-m3.json`에 캐시한다. 처음 없으면 고정 URL에서 내려받고 SHA-256을 검증한다. 이 파일은 Git에서 제외한다. 필요하면 `RAG_TOKENIZER_PATH`로 위치를 지정할 수 있다.
- 추가 스키마: `database/migrations/20261021_department_document_chunks.sql`. 기존 RAG 가져오기 스키마 뒤에 적용하며 서버·워커 시작 시에도 멱등 적용한다.
- 기존 원문, 벡터, 계정을 갱신하는 SQL은 없다. 운영 DB에서 `database/init.sql`을 다시 실행할 필요가 없다.

## 검증

- 기존 동작을 포함한 백엔드 119개 테스트 통과(환경 의존 테스트 1개 건너뜀). 이후 조문 경계·종료 처리·외부 짧은 자료 참조를 포함한 관련 21개 테스트도 모두 통과했다.
- 현재 관리자 화면 테스트 81개 및 진행률 테스트 4개 통과, 프런트 빌드 성공.
- 별도 임시 DB에서 실제 BGE-M3와 기존 채팅 서버 연동: 9,680토큰 원문 1개와 짧은 원문 2개를 처리했다. 짧은 자료 2개가 먼저 저장되고, 긴 자료는 5개 조각으로 저장됐다. 긴 원문 전체는 임베딩 요청에 포함되지 않았다. 채팅이 멀리 있는 예외와 별표의 제외 차량을 답변에 반영했다.
- 실제 `final.csv` 49행은 199,590자·109,273토큰이다. 길이 판별 약 0.45초, 분할 약 0.90초, 669개 조문 구간, 조각 최대 1,415토큰으로 확인했다. 원문 문자 손실은 없었다. 이 검증은 실제 파일을 DB에 삽입하거나 전체 임베딩한 작업이 아니다.
