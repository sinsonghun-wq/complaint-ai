# 선택 부서의 민원 전체 삭제

`선택 카테고리 삭제`를 `부서 민원 전체 삭제`로 변경했다.
선택한 담당 부서의 활성 보관함에 있는 민원을 전부 삭제 보관함으로 이동한다.

- 접수 대기·접수 됨·완료·취소 상태를 모두 포함한다.
- 파일 업로드·민원인 작성 여부, 출처 필터, 페이지 크기·현재 페이지와 무관하다.
- 다른 부서와 이미 삭제 보관함에 있는 민원은 변경하지 않는다.
- 담당 부서 관리자만 실행할 수 있다. 기존 삭제 확인 메시지를 앱 내부 경고창에 유지한다.
- 사유 입력은 생략하고 기존 기본 사유인 `해당 민원은 잘못된 사유로 인해 취소되었습니다.`를 모든 대상에 자동 적용한다.
- 버튼 활성화는 출처 필터가 적용되지 않은 부서 전체 건수를 사용한다.
  필터 결과가 0건이어도 해당 부서에 민원이 남아 있으면 실행할 수 있다.
- 기존 삭제 보관함 정책을 사용하며, 완료 답변과 이전 상태를 보존한다.
  완료 민원을 복원하면 완료 상태와 전송된 답변을 유지한다.
- 개별 민원의 삭제·수정 조건, 다른 부서 권한, DB/임베딩/RAG 설정은 변경하지 않았다.

API: `DELETE /api/departments/{department_id}/complaints`와 기존 이름 기반 경로.
상태 조건을 제거하고 부서 ID 및 `deleted_at IS NULL`만으로 대상 행을 잠근다.

## 버튼을 눌러도 남아 보였던 원인과 보완

점검 시 실제 백엔드 로그에는 개별 삭제 요청만 있었고 부서 전체 삭제 요청은 없었다.
기존 코드는 브라우저 `window.confirm` 뒤에 별도 `window.prompt`를 요구했다.
두 번째 사유 입력이 취소되거나 빈 값이면 안내 없이 종료해 DELETE 요청을 보내지 않았다.
따라서 경고 확인만으로는 이동하지 않는 구조였다. 과거 사용자가 어느 대화상자에서
중단했는지는 서버 로그만으로 확정할 수 없다.

또한 서버 성공 후에도 목록을 즉시 비우지 않고 건수와 목록의 재조회에 의존했다.
재조회가 실패하면 이전 목록이 남고 성공 메시지 대신 조회 오류를 표시했다.
삭제 중 자동 조회와 이미 진행 중인 조회도 일괄 무효화하지 않았다.

현재는 앱 내부 경고창에서 `삭제된 데이터로 이동`을 한 번 확인하면 기본 사유를 전송한다.
처리 중 중복 실행·경고창 닫기·자동 조회를 막는다. 이동 전 조회 응답은 목록과 집계에
반영하지 않는다. 서버가 이동을 확인하면 목록·건수·페이지·선택한 접수 민원을 즉시 갱신한다.
후속 조회가 실패해도 확인된 이동 결과는 유지하며 재조회 오류를 따로 안내한다.
서버의 집계에서 생략된 빈 부서도 0건으로 처리해 삭제 버튼이 다시 활성화되지 않게 한다.
삭제된 데이터 화면은 진입할 때 보관 목록과 집계를 새로 가져온다.

별도 테스트 DB에서 모든 상태·출처 조합, 다른 부서/미분류/기존 보관함 유지,
원본·기본 사유·완료 답변 보존과 복원, 활성 목록 0건 및 삭제 보관함 포함을 확인했다.
민원인에게는 기존 동작대로 관리자 취소 사유를 표시한다.
UI 검사는 경고 취소, 기본 사유 자동 적용, 지연 조회, 중복 클릭, 이동 실패와 재시도,
이동 후 조회 실패, 삭제된 데이터 화면 이동까지 검증한다.
현재 앱에서는 경고창 표시와 취소를 확인했으며 실제 민원 17건을 테스트로 이동시키지 않았다.
