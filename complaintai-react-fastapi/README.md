# ComplaintAI React + FastAPI 이식본

기존 정적 JavaScript + Node/Express 구현을 보존한 채 별도로 만든 React + Python/FastAPI 구현이다.

## 일반 민원인 접수 흐름

- `POST /api/complaints`는 원문을 먼저 저장하고 즉시 접수 응답을 반환한다. 화면은 작성한 민원으로 이동하며, 요약·분류 진행 안내는 표시하지 않는다.
- 최초 업무 상태는 `접수`(화면: 접수 대기), 카테고리는 NULL이다. 화면에는 제목·원문과 `부서 판별중...`을 표시하며, 3초 간격 목록 갱신으로 분류된 부서를 표시한다.
- 요약·분류는 FastAPI 응답 이후 백그라운드 작업으로 실행한다. DB의 `analysis_state`(pending/processing/completed/cancelled)와 `analysis_revision`으로 업무 상태와 분석 진행 상태를 구분한다. 서버 시작 시 중단된 pending/processing 작업을 다시 처리한다. 현재 단일 Uvicorn 프로세스 기준이며, 다중 웹 서버 배포 시 별도 큐·작업 lease로 이전해야 한다.
- 수정은 접수 대기에서만 허용하며, 같은 민원 ID에서 원문을 교체하고 기존 요약·카테고리·벡터를 비운 뒤 버전을 증가시켜 다시 분류한다. 물리적인 행 삭제·재생성이 아닌 원자적 교체로 참조 관계를 보존한다.
- 민원인이 삭제하면 즉시 취소 및 삭제 보관함으로 이동한다. 작성한 민원에서는 사라지고, 관리자는 기존 취소 안내를 확인한다. 답변 완료·취소 상태의 기존 수정/삭제 제한은 유지한다.
- 이전 버전 분석·임베딩은 조건부 UPDATE로 무시하므로 삭제한 민원을 되살리거나 새 내용을 덮어쓰지 않는다. 부서 분류 결과는 임베딩 완료를 기다리지 않고 먼저 공개한다.


## 현재 부서·분류 체계

노동·기업 / 교통·국토 / 주택·건축 / 환경·위생 / 문화·행정·안전 / 보건·복지 / 기타

`app/departments.json`을 백엔드와 React가 함께 읽는다. 분류 카테고리, 부서별 권한, 전달 목록, LLM 프롬프트·규칙 기반 분류가 이 목록을 사용한다. 노동과 기업의 키워드는 노동·기업으로, 교통과 건설·국토의 키워드는 교통·국토로 모두 합쳤다(추가 요청한 세부 키워드 포함). 주택·건축 등 나머지 5개 부서는 유지한다. 모델은 기존 qwen2.5:7b-instruct이며 프롬프트 버전은 complaintai-ko-seven-context-v4다. 모델 파인튜닝을 수행한 것은 아니다.

### 문맥·가중치·LLM 재판단 규칙

- `app/rule_classifier.py`가 제목/본문을 검사한다. 대기는 주변 24자에 환경·오염·대기질 등의 근거가 있고 대기 시간/순번 등의 표현이 없을 때만 환경 점수를 준다. 인도는 보행·도로·파손 등 문맥에서만 점수를 주며 상품 인도·인도네시아는 제외한다. 공사도 시공/도로/현장 등의 문맥을 요구하고 공기업명은 제외한다. 정규식 기반 조건이지 완전한 자연어 의미 분석은 아니다.
- 일반 키워드는 1점, 등록된 구체 표현은 3점이다. 층간소음은 주택·건축, 임대/전세 보증금은 주택·건축, 공장/공사장 소음은 환경·위생을 우선한다. 일반 보증금은 계약 대상 확인이 필요하므로 LLM으로 보낸다. 같은 표현 안의 짧은 키워드, 띄어쓰기 변형 및 반복은 중복 가산하지 않는다.
- 규칙 자동 확정은 1위가 3점 이상이고 2위와의 차이가 2점 이상인 경우만 허용한다. 양수 점수 동점, 1점 차이, 1~2점의 약한 근거는 LLM으로 재판단한다. confidence=0.4/0.85 등은 정책 지표이지 실측 정확도가 아니다.
- CSV 워커와 PDF/HWP/XLSX 배치 저장 모두 위 저확신 조건을 사용한다. 일반 민원은 기존처럼 LLM을 시도한다. LLM 사용 설정/동시 요청 제한/실패 시 규칙 대체/500건 저장은 유지한다. `needs_review`가 true라는 이유로 필요한 LLM 호출을 생략하지 않는다. LLM 실패·비활성화 시 애매한 규칙 결과는 검토 필요로 남긴다.
- 모든 점수가 0인 것은 근거 부재로 구별한다. 대량 CSV의 기존 성능 정책(키워드 없는 본문 80자 이상은 기타로 유지)은 그대로이며 이 경우 검토 필요로 기록한다. 일반 보증금처럼 명시적으로 모호한 표현은 이 예외보다 먼저 LLM에 전달한다. 애매한 행 비율이 높은 파일은 LLM 호출 증가로 처리 시간이 늘어날 수 있다.
- `analysis_metadata`에 `confidence`, `rule_decision`(부서별 점수/차이/매칭/제외 문맥/LLM 필요 사유), `llm_attempted`를 기록한다. 테이블/계정/기존 민원을 변경하지 않으며 기존 민원을 자동 재분류하지 않는다. 변경 후 서버/CSV 워커를 재시작한다.

기존 9개 부서 DB는 서버와 워커를 중단하고 `python scripts/merge_to_seven_departments.py --apply`로 이전한다. `--apply` 없이 실행하면 대상만 확인한다. 기존 민원·일반 사용자와 테이블 구조는 지우거나 변경하지 않는다. 통합 대상 관리자 4개(노동/기업/교통/건설·국토)만 삭제하고 새 ID/소유자 ID의 관리자 2개로 교체한다. 다른 5개 관리자는 ID·비밀번호·이름을 유지한다. 기존 민원/삭제 보관함의 부서, 답변·문서 작성자, CSV 작업 소유자, 헤더 매핑 작성자 및 조직 소속도 이전한다. 민원 제목·원문·상태·답변은 유지하며 통합되지 않은 부서 민원은 재분류하지 않는다. 삭제된 관리자 계정의 이전 토큰은 무효다.

기존 벡터는 모두 보존하여 검색 기능이 중단되지 않도록 한다. 부서가 바뀐 기존 벡터는 옛 부서명을 포함하므로 `analysis_metadata.department_merge.needs_reembedding=true`로 표시하고 필요하면 순차 재임베딩한다. 검색 권한/필터는 새 DB 부서명으로 적용되며 신규 민원 임베딩은 새 부서명을 사용한다. 재실행은 멱등적이며 계정 충돌 시 전체 트랜잭션을 롤백한다. 워커가 실행 중이거나 처리 중인 파일 작업이 남아 있으면 이전을 거부한다. 서버를 재시작하고 React를 다시 빌드해야 화면/권한/분류 설정이 함께 적용된다.

`migrate_to_seven_departments.sql`과 `migrate_to_nine_departments.py`는 과거 이력용이며 현재 버전에 실행하면 안 된다. 부서 통합에 `database/init.sql`을 사용하지 않는다.

## 실행

```powershell
cd complaintai-react-fastapi
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env

# React 개발 서버(처음 한 번 npm install 필요)
cd frontend
npm install
npm run build
cd ..

# 터미널 1: FastAPI가 frontend/dist를 제공한다.
uvicorn app.main:app --host 127.0.0.1 --port 8000

# 터미널 2: 대용량 CSV 작업 전용 워커를 별도로 실행한다.
.\scripts\run_import_worker.ps1
```

브라우저에서 `http://127.0.0.1:8000`을 연다. 개발 중에는 `frontend`에서 `npm run dev`를 별도로 실행할 수 있다.

CSV 작업은 PostgreSQL 작업 큐에 등록되고 별도 워커가 처리한다. 웹 서버를 재시작해도 워커가 계속 실행 중이면 작업은 유지된다. 워커가 중단돼 heartbeat가 5분 이상 갱신되지 않은 작업은 `실패`로 전환되며, 업로드 화면의 `재처리` 버튼으로 마지막 500건 저장 지점부터 다시 시작할 수 있다.

로컬 실행에서는 CSV 업로드(매핑 확정 완료), 수동 매핑 확정, 재처리 요청 시 워커가 없으면 자동으로 실행한다. 워커는 PostgreSQL 세션 advisory lock으로 중복 실행을 방지하며, 웹 서버와 독립적으로 실행된다. 단순 조회나 서버 시작만으로는 중단된 작업을 자동 재개하지 않는다. 워커 실행 실패는 HTTP 503 안내로 반환한다. 컨테이너 등 배포 환경에서는 별도 워커 서비스 운영을 권장한다.

## 민원 상태와 권한

| 상태 | 민원인 수정 | 민원인 삭제(취소) | 관리자 답변 | 관리자 삭제(취소) |
|---|---|---|---|---|
| 접수 대기 | 가능 | 가능 | 가능 | 사유 입력 후 가능 |
| 접수 됨 | 불가 | 가능 | 가능 | 사유 입력 후 가능 |
| 완료 | 불가 | 불가 | 불가 | 불가 |
| 취소 | 불가 | 불가 | 불가 | 불가 |

- 관리자가 `민원 접수`로 원문을 열면 화면 상태가 `접수 대기 → 접수 됨`으로 바뀐다. 기존 데이터와 처리 규칙의 호환성을 위해 DB/API 상태 값 `접수`, `진행중`은 유지하며, 화면에서는 각각 `접수 대기`, `접수 됨`으로 표시한다.
- 답변 임시 저장은 완료가 아니다. 답변 전송 시에만 `완료`로 바뀐다. 초안을 지워도 이미 확인한 민원은 `진행중` 상태를 유지한다.
- 민원인이 취소하면 본인 목록에서 사라지고, 관리자 목록에는 취소 안내만 남는다. 관리자가 취소하면 민원인 목록에 취소 사유가 표시된다. 관리자에게는 취소된 원문·답변을 반환하지 않는다.
- 취소 사유와 주체는 DB에 보존한다. 업무상 취소(`complaint_status`)와 기존 보관함 삭제(`deleted_at`)는 구분한다. 취소된 민원은 복원할 수 없다.
- 민원 접수 화면은 2초마다 최신 상태를 확인해 취소·부서 변경 시 답변 입력을 닫는다. 서버는 행 잠금으로 취소와 답변 전송의 동시 실행을 차단한다.
- 완료 민원의 `재민원 작성`은 새 접수 건을 만들고 이전 제목·원문·전송 답변을 `previous_context` 스냅샷으로 보존한다. 재민원은 이전 담당 부서로 전달된다.
- 카테고리 일괄 취소는 사유를 요구하며 완료·취소 건은 제외한다. 예외적으로 `분류 카테고리 전체 삭제 (테스트)`는 모든 부서의 미삭제 민원(완료·취소 포함)을 취소 상태로 변경하고 `deleted_at`을 기록해 삭제된 데이터 보관함으로 이동한다. 원본 및 최종 답변은 DB에 보존하고 임시 답변만 제거한다. 운영 배포 전에 제거해야 하는 테스트 전용 기능이다.
- FastAPI 시작 시 일부 호환 컬럼을 추가한다. 팀원 DB 구조를 완전히 맞출 때는 루트 `database/init.sql`로 프로젝트 테이블을 삭제·재생성한 뒤 데이터를 복원한다. 이 파일은 데이터 보존용 마이그레이션이 아니다. 절차는 `database/README.md`를 확인한다.

검증: `python -m unittest discover -s tests -v` (설정된 PostgreSQL 사용, 테스트 생성 데이터만 정리, LLM/임베딩 호출은 대체하여 업무 규칙 검증).

## 문서 추출 방식

삭제된 데이터 보관함 하단의 `삭제된 데이터 전체 영구 삭제 (테스트)`는 관리자 비밀번호 확인 후 모든 부서의 삭제된 데이터를 상태·출처 필터·페이지와 관계없이 제거한다. 취소된 데이터도 포함하며, 미삭제 민원은 제거하지 않는다. 모든 관리자에게 임시로 허용하는 테스트용 예외 권한이며 일반 사용자는 API에서도 차단한다. 영구 삭제는 복구할 수 없다. 운영 배포 전에 제거하거나 권한을 재설계해야 한다.

- CSV 인코딩은 UTF-8 BOM을 우선 확인하고, BOM 없는 UTF-8 샘플은 마지막 문자가 잘려도 오판하지 않도록 증분 디코더로 검사한다. 인코딩·CSV 읽기 오류는 안내가 포함된 HTTP 422로 반환한다.
- PDF·HWP·XLSX·XLS는 500건을 넘어도 추출 결과를 자르지 않는다. 현재 웹 화면은 전체 추출 결과를 받은 뒤 최대 500건씩 순차 저장 요청을 보내며, 각 민원을 독립적으로 분류·저장한다. 저장 API도 요청을 500건 단위 트랜잭션으로 나누며, 화면은 묶음 완료마다 진행률을 갱신한다.
- 문서 추출 자체는 전체 결과를 메모리에 모으는 방식이며, CSV와 달리 별도 워커의 재시작·재개 기능을 사용하지 않는다. 초대형 문서용 스트리밍 추출·작업 큐 연동은 별도 보완 항목이다.

- XLSX: `openpyxl`로 모든 시트를 순회한다. 각 시트에서 `제목`과 `신청원인`(또는 민원 본문 열)이 함께 있는 헤더 행을 찾고, 이후의 각 행을 별도 민원으로 처리한다. 안내 시트는 자동으로 건너뛴다.
- PDF: 페이지별로 `pypdf`와 `pdfplumber`의 텍스트 추출 결과를 비교한다. 제목·`신청원인` 구조를 가진 페이지는 각각 하나의 민원으로 분리한다. 텍스트 품질이 낮은 페이지에만 PyMuPDF 렌더링과 Tesseract OCR을 재시도한다.
- HWP: `hwp5txt`(pyhwp)가 있으면 먼저 텍스트를 추출한다. 낮은 품질이면 LibreOffice의 HWP-to-PDF 변환 결과를 PDF/OCR 흐름으로 다시 처리한다. Windows에서 HWP는 별도 설치가 필요하므로 `hwp5txt` 또는 LibreOffice가 없는 환경에서는 업로드가 안내 오류로 끝난다.

### HWP 파서 준비

HWP 기능은 프로젝트에 포함하지 않는 별도 파서 환경을 사용한다. 새 컴퓨터에서 처음 한 번 다음을 실행한다. Python 3.11과 인터넷 연결이 필요하다.

```powershell
cd C:\경로\complaintAI\complaintai-react-fastapi
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\setup_hwp_parser.ps1
```

성공하면 `.hwp-parser\Scripts\hwp5txt.exe`가 생성된다. 이 폴더는 Git에 올리지 않으며, FastAPI 서버는 해당 실행 파일을 자동으로 찾는다. 파서 또는 LibreOffice를 찾지 못한 경우에는 서버가 HTTP 500 대신 설치 안내가 담긴 HTTP 503을 반환한다.

현재 HWP 표는 `hwp5txt`가 표의 셀 배치를 보장하지 않으므로, 표 구조를 그대로 보존하는 처리(예: `hwp5html` 기반 셀 파싱)는 별도 보완 항목이다.
